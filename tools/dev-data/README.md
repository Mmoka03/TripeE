# 교토 개발 데이터 등록

기존 [교토 검수본](../../docs/kyoto-content-draft.md)의 문안·좌표·사진을 로컬 개발 DB에 등록함.
새 자료 수집이나 AI 생성을 실행하지 않음. B의 최종 콘텐츠 승인과 운영 환경 게시는 별도임.

## 실행

Node.js 24와 Docker Compose를 사용함. [개발 DB](../../docs/docker-development.md)를 시작하고
앱 계정 준비 명령을 실행한 뒤 [백엔드](../../backend/README.md)를 `postgres` 프로필로 실행함.
백엔드와 이 도구가 같은 `infra/.env`의 Compose DB를 사용해야 함.
DB 이름·포트를 변경했다면 백엔드 환경 변수에도 동일하게 적용함.

저장소 루트의 별도 터미널에서 실행함. Windows와 Mac 모두 같은 명령을 사용함.

```sh
pnpm --dir tools/dev-data install --frozen-lockfile
pnpm data:kyoto
pnpm dev
```

기본 백엔드 주소는 `http://127.0.0.1:8080`임. 다른 로컬 포트라면 등록 명령에
`TRIPEE_API_ORIGIN` 환경 변수를 설정하고 `frontend/vite.config.js`의 프록시 주소도 맞춤.
등록 도구는 원격 서버에 실행할 수 없도록 제한함.

- 실제 화면: `http://127.0.0.1:5174/?cityName=Kyoto`
- 기존 다수 핀·상태별 디자인 시연: `http://127.0.0.1:5174/?demo=1`
- 관리자 화면은 아직 브라우저 저장소를 사용하는 시연 화면임. 이 등록 도구는 실제 관리자 API를 사용함.

## 등록 범위

- 일본·도시 태그 3개, 로컬 등록용 관리자 계정을 준비함.
- 교토 도시와 초안을 생성하고 사진 업로드 → 출처 연결 → 초안 저장 → 게시 검증 → 게시 순으로 처리함.
- 대표 경험 4개를 저장하고 후시미이나리·아라시야마·니시키시장 3개를 선정함.
- 방문 시기·도시 접근·현지 이동·고려사항을 각 1개 등록함.
- 사진은 저장소의 교토 사진 1장을 사용함. 저작자·출처·라이선스·가공 내용을 함께 저장함.
- 안전정보는 `UNVERIFIED`로 유지함. 도시 ID는 DB가 생성하며 고정값을 가정하지 않음.

SQL은 계정·사전 준비와 기존 데이터 조회에 사용함. 도시 콘텐츠는 실제 관리자 API를 거쳐
편집 잠금·게시 조건·감사 이력을 적용함. 원문 검수일은 근거 메모에 별도로 남기며,
API의 `checkedAt`은 이번 등록 검토 시각임. 이번 실행을 신규 원문 재검수로 기록하지 않음.

## 재실행과 로컬 파일

이미 게시된 교토는 사진 제공 여부만 확인하고 콘텐츠와 이력을 변경하지 않음.
게시 이력이 있는 비공개 도시는 자동 게시하지 않으며, 다른 관리자가 작성한 초안도 덮어쓰지 않음.
중간 실패 시 생성한 비공개 초안은 남으며 같은 등록 계정이 작성한 미게시 초안만 이어서 처리함.
전체 등록을 하나의 DB 트랜잭션으로 묶는 방식은 아님.

`.local-archive/kyoto-import-admin.json`에는 무작위로 만든 로컬 관리자 자격 증명,
`kyoto-import-result.json`에는 등록한 도시 ID를 보관함. 두 파일은 Git에서 제외됨.
도시를 삭제하거나 DB를 교체한 경우 등록 기록을 임의 재사용하지 말고 먼저 대상을 확인함.
실행 중 강제 종료로 `kyoto-import.lock` 폴더가 남았다면 다른 등록 작업이 없는지 확인한 뒤 정리함.
사진 원본 파일은 백엔드의 `data/photos/`에 저장되므로 DB 볼륨과 함께 보존해야 함.
현재 백엔드의 PNG 변환으로 교토 사진은 약 9.4 MiB임. 실제 배포 전에는 화면 크기에 맞는
축소 이미지 제공과 전송 용량 최적화가 필요함.

## 검증

```sh
pnpm test:data
pnpm --dir tools/api-contract test:live
```

첫 명령은 문안·출처 연결·좌표·사진 해시를 검사함. 두 번째는 실행 중인 서버의 HTTP 응답을
OpenAPI와 비교함. 도시 준비 중 상태 등 DB에 없는 사례는 건너뛰므로 전체 상태 검증을 대신하지 않음.
