# 백엔드 테스트 명세

검토할 API를 찾고, 입력값과 절차를 확인한 뒤 테스트를 작성할 때 사용하는 문서 모음이다.

- **상태:** 설계 초안. 실제 테스트 실행 결과는 별도 기록한다.
- **최근 문서 검토일:** 2026-11-24. API 정책·OpenAPI·현재 작업 트리를 대조했다.

## 목적에 따라 읽기

처음 전체를 읽을 때는 1~4 순서로 진행한다. 특정 작업만 하려면 필요한 문서부터 연다.

| 순서 | 확인할 내용                               | 문서                                                             |
| ---- | ----------------------------------------- | ---------------------------------------------------------------- |
| 1    | 검증 범위·우선순위·완료 기준              | [전체 테스트 설계](test-equivalence-partitions-draft.md)         |
| 2    | API 39개 작업과 케이스·기존 테스트의 연결 | [API별 테스트 찾기](api-operation-test-matrix.md)                |
| 3    | 준비 데이터·입력값·실행 순서·기대 결과    | [실행 상세 명세](test-case-execution-draft.md)                   |
| 4    | 개인정보·법령의 적용 조건과 추가 검증     | [국내 법령 검증](korea-legal-security-test-review-2026-11-23.md) |

검증 계약은
[API 정책](../api-v1.md)·[OpenAPI](../openapi-v1.json)·[DB 제약조건](../db-constraints-v1.md)을
참고한다. 실행 도구와 Gradle 명령은 [백엔드 실행 안내](../../../backend/README.md)에 있다.

테스트를 구현하면 각 케이스 ID에 테스트 클래스/메서드·실행 커밋·결과 근거를 연결한다. 코드와 계약의
차이는 검토 이슈로 기록하고 실제 응답에 맞춰 기대값을 임의 변경하지 않는다.

## ID와 용어

ID는 문서를 오가며 같은 항목을 찾기 위한 이름이다.

| ID              | 의미                                                |
| --------------- | --------------------------------------------------- |
| OP              | HTTP 메서드·경로로 구분한 API 작업                  |
| C·P·A·D·W·M·I·H | 공통·공개 조회·인증·도시·초안·사진·AI·이력 요구사항 |
| F / Q           | 개별 입력값 묶음 / 여러 단계로 진행하는 시나리오    |
| B / X           | 조건·분기 검증 / 추가 테스트 기법                   |
| S / R / L       | 보안 / 배포 / 법령 검증                             |
| G               | 아직 결정하거나 대조해야 할 계약·정책 쟁점          |

| 문서의 용어 | 읽는 뜻                                         |
| ----------- | ----------------------------------------------- |
| fixture     | 계정·도시·사진 등 테스트 전에 준비할 데이터     |
| assertion   | 실제 결과가 기대값과 맞는지 확인하는 검사       |
| snapshot    | 요청 전후를 비교하기 위해 확보한 데이터 상태    |
| mock / 목   | 실제 DB·외부 서비스 대신 사용하는 테스트 대역   |
| leaf case   | 값·상태·계층을 하나로 확정해 개별 실행할 테스트 |

문서의 숫자는 실행 건수가 아니다. F01에 입력값이 여러 개 있으면 각각 개별 케이스로 실행하고
기록한다.

## 2026-11-23 재평가

**문서 수준은 구현을 시작할 수 있는 설계 초안(상위 명세의 자체 기준3단계)이다.** 경로 단위 연결은
보강했지만, 개별 입력 조합별 assertion·현재 커밋 실행 증거·운영 목표가 없어 실행 검증 완료 단계로
올리지 않는다. 기존 테스트의 제품 품질과 이번 문서의 품질은 별도다.

| 계약·정책 분리 | 제안과 현재 코드가 같은 기대값으로 읽힐 수 있음         | G 쟁점 등록부, 근거/설계/자동화/실행 상태 분리                          | API 검토자·운영 담당의 계약/정책 결정                            |
| 보안·법령      | 기본 보안 테스트만으로 운영 의무까지 완료로 오인 가능   | 기존 일부 구현과 L 계획 미실행을 구분, 부정확한 타법 비교 제거          | 적용 범위·권한 회수·접속기록·보유/파기 운영 증거 확인            |
| 사용·유지 관리 | ID 체계·문서 수·이동 전 경로·이전 평가 표현 잔류        | 안내·상호 링크·대표/leaf ID·별칭/분모 규칙 정리                         | 계약 변경 시 OP·케이스·예시·쟁점을 함께 갱신                     |

현재 범위는 F01~F42, Q01~Q05, B01~B12, X01~X13, S01~S20, R01~R20, L01~L17이다. 각 계층·값·상태를
개별 케이스로 펼친 뒤 같은 집계 단위로 기록한다.

## 출시 후보에서 실행할 항목

1. 후보 아티팩트, 환경 버전, 고정 데이터와 실행 결과를 묶어 기록한다.
   [실행 순서와 결과물](test-case-execution-draft.md#릴리스-후보-실행-순서와-결과물)
2. 초안 저장 충돌·세션 만료·CSRF·안전정보 버전 충돌·게시 Location은 케이스 단위로 기대 응답과
   후조건을 확인한다. [출시 필수 검증 연결](api-operation-test-matrix.md#출시-필수-검증-연결)
3. 관리자 기능이 출시 범위에 포함되면 실제 브라우저에서 게시와 익명 조회, 오래된 탭, 안전정보
   재검토, 기존 세션 회수, 응답 유실을 확인한다.
   [관리자·공개 UI 실행 절차](test-case-execution-draft.md#r11-실제-사용자-흐름)
4. 운영 목표와 중단 기준을 확정해 배포 전 판정과 배포 직후 트래픽 확대 판단에 적용한다.
   [배포 단계와 합격 기준](test-equivalence-partitions-draft.md#17-배포-검증-순서와-합격-기준)

## 구현 착수와 완료 판단

1. API별 연결 문서에서 작업 하나를 골라 정상 요청·핵심 P1 거부·실패 후 상태를 선택한다. 기존
   테스트의 이름뿐 아니라 준비 데이터·assertion을 대조해 재사용한다.
2. G 등록부와 충돌하면 “현재 구현 관찰”과 “승인된 기대 계약”을 나누고 정책차단으로 기록한다. 범위와
   독립적인 케이스는 진행한다.
3. 케이스별로 ID·계층·예상 결과·부작용·환경을 고정한 뒤 테스트한다. 신규 동작은 실패→최소
   구현→통과→리팩토링 결과를 남긴다.
4. API/법령/운영 목표가 바뀌면 문서 검토일·코드 기준·근거·영향 OP·케이스를 갱신한다. 오래된 보고서
   숫자를 현재 커밋 결과로 복사하지 않는다.
5. 기존 자동화 통과·새 케이스 실행·계약/DB 검증·미해결 항목·스킵/차단을 각각 보고한다. 정책 미정이나
   환경 차단을 통과로 계산하지 않는다.

현재 문서 검증은 상대 링크·케이스/작업 ID·OpenAPI 작업 집합·JSON 예시·형식의 일관성 확인으로
제한한다. 백엔드 기능·보안·운영의 실제 시험 실행은 해당 실행 기록으로 별도 증명해야 한다.
