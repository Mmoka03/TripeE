## 실행 전 준비

- 격리 테스트에서 앱 로거를 캡처하고, 스테이징에서는 실제 프록시·앱·수집기 중 배포에 포함된 경로로
  같은 케이스를 실행한다. 해당 케이스의 시간 범위·버전·로그 출처를 기록한다. 제품 로그 형식이
  정해졌다면 파싱한 필드를 비교하고, 기존 텍스트 로그는 로거·레벨·식별자를 비교한다.
- 다른 요청과 구분되는 가짜 값과 테스트 계정을 사용한다. 로그 캡처에는 정상 이벤트가 수집되는지 먼저
  확인해, 누출이 없다는 결과가 로그 수집 누락 때문에 나오는 경우를 걸러낸다.
- 아래 항목은 실행 계획이다. 배포 로그의 필수 필드·보유 기간·알림 기준·수집 유실 허용 범위는 승인된
  운영 정책을 사용한다. 필수 정책이나 환경이 없으면 해당 판정을 차단으로 기록한다.

## LOG01 DB 오류 응답과 서버 로그 연결

1. 공개 목록의 정상 요청을 먼저 보내 `200`을 확인한다. 기존 MVC 클래스에서는 `CityListService`
   대역이 검증 지점이다. 이 대역에서 `DataAccessResourceFailureException`을 던지도록 구성하고 예외
   메시지에 `TEST_LOG_DB_DETAIL_01`을 넣는다. 동일한 `GET /api/v1/cities`를 보낸다.
2. 응답에서 `500 INTERNAL_ERROR`, 비어 있지 않은 `traceId`, `Cache-Control: no-store`를 확인한다.
   `ApiProblems`의 ERROR 로그에서 해당 경로와 응답의 `traceId`가 일치하는 항목을 찾는다. 응답과 앱
   로그에 예외 메시지의 가짜 값이 없는지 확인한다.
3. 같은 경로에서 실패 요청을 2개 동시에 실행한다. 응답의 ID가 서로 다르고 각 ID가 그 요청의 ERROR
   로그에 한 번씩 나타나는지 확인한다. 정상 대조군에는 같은 로거의 DB 오류가 없어야 한다.
   [기존 MVC 테스트](../../../backend/src/test/java/com/tripee/backend/city/CityListControllerTest.java)

### 기존 MVC 테스트에 로그 검사 추가

아래 메서드는 `CityListControllerTest`의 `mvc`, `cities`와 기존 정적 import를 사용한다. `Logger`,
`Level`은 `ch.qos.logback.classic`, `ILoggingEvent`는 `ch.qos.logback.classic.spi`, `ListAppender`는
`ch.qos.logback.core.read`에서 가져온다. `ApiProblems`는 `com.tripee.backend.common.exception`,
`JsonMapper`는 `tools.jackson.databind.json`, `LoggerFactory`는 `org.slf4j`, `assertThat`은
AssertJ를 사용한다.

```java
@Test
void matchesDatabaseErrorTraceIdToOneServerLog() throws Exception {
  String marker = "TEST_LOG_DB_DETAIL_01";
  var logger = (Logger) LoggerFactory.getLogger(ApiProblems.class);
  var captured = new ListAppender<ILoggingEvent>();
  captured.start();
  logger.addAppender(captured);
  try {
    when(cities.list(null)).thenThrow(new DataAccessResourceFailureException(marker));
    var response = mvc.perform(get("/api/v1/cities"))
        .andExpect(status().isInternalServerError())
        .andExpect(header().string("Cache-Control", "no-store"))
        .andExpect(jsonPath("$.code").value("INTERNAL_ERROR"))
        .andReturn().getResponse();
    String traceId = new JsonMapper().readTree(response.getContentAsByteArray())
        .path("traceId").asString();
    assertThat(traceId).isNotBlank();
    assertThat(captured.list)
        .filteredOn(event -> event.getLevel().equals(Level.ERROR))
        .filteredOn(event -> event.getFormattedMessage().contains("traceId=" + traceId + ")"))
        .singleElement()
        .satisfies(event -> {
          assertThat(event.getFormattedMessage()).contains("/api/v1/cities").doesNotContain(marker);
          assertThat(event.getThrowableProxy()).isNull();
        });
    assertThat(response.getContentAsString()).doesNotContain(marker);
  } finally {
    logger.detachAppender(captured);
    captured.stop();
  }
}
```

먼저 한 요청에 대해 확인한다. 동시성 케이스에서는 각 작업의 HTTP 응답에서 식별자를 얻고, 두 작업이
종료된 후 ID마다 한 건씩 대응하는지 검사한다. 토큰과 원본 예외의 비노출 검사는 LOG03도 함께
적용한다.

## LOG02 접근 로그의 상태와 요청 경계

접근 로그를 활성화한 배포 설정으로 `GET /api/v1/cities`의 `200`, `countryCode=jp`의
`400 INVALID_QUERY`, 익명 `GET /api/v1/admin/session`의 `401 AUTH_REQUIRED`,
[LOG01](#log01-db-오류-응답과-서버-로그-연결)의 `500`을 각각 실행한다. 시험 요청 전후를 같은
설정으로 수집한다.

로그 사용 정책에서 수집 대상으로 정의한 요청은 기록된 시각·메서드·경로 또는 라우트·HTTP 상태·처리
시간이 실제 요청과 일치해야 한다. 프록시에서 거부한 요청은 프록시 기록에서 확인한다. 일반 4xx가 서버
장애 알림으로 집계되는지는 경보 규칙에 따라 확인한다. 공통 요청 ID가 도입되면 각 계층의 동일 값 또는
계약에 정의된 대응 관계를 확인한다.

## LOG03 비밀번호·토큰·내부 정보 비노출

- 로그인 실패 요청에는 `TEST_LOG_PASSWORD_03`을, CSRF 거부 요청에는 `TEST_LOG_CSRF_03`을 사용한다.
  정상 인증·편집 요청에는 실제 테스트 세션에서 발급받은 쿠키·CSRF·편집 토큰을 사용한다. DB 예외,
  사진 저장 실패, 활성화된 경우 AI 실패도 독립 실행하며 설정값은 모두 테스트 전용이다.
- 앱 표준 출력·오류, 프록시 로그, 중앙 수집 기록, 해당 감사 JSON, 오류 응답을 검사한다. 가짜
  비밀번호, 쿠키·토큰 원문, 공급자 키, 내부 SQL과 실제 파일 경로의 예상 밖 노출은 0건이어야 한다.
  정상 응답에서 계약상 클라이언트에 발급하는 쿠키·토큰은 지정된 위치에서만 확인한다.
- 테스트 보고서에는 항목별 검출 건수와 로그 위치를 남긴다. 정상 인증에서 얻은 토큰이나 검출된 비밀값
  원문은 보고서에 복사하지 않는다. [S13](test-case-execution-draft.md#s13-비밀정보-노출)

## LOG04 사진 정리 실패와 재시도

1. 테스트 사진 저장소 아래에 하위 파일이 들어 있는 디렉터리를 만들고, 그 이름을 정리 작업 키로
   사용한다. 삭제 실패 시 WARN 한 건과 대기 작업 유지 여부를 확인한다. 기존 서비스 테스트의 비어
   있지 않은 디렉터리 fixture를 재사용할 수 있다.
2. 하위 파일을 제거한 뒤 정리를 다시 실행한다. 디렉터리 삭제와 작업 완료를 확인하고, 같은 작업에
   추가 실패 WARN이 없는지 검사한다. 성공 재처리는 저장소와 파일 상태로 판정한다.
3. WARN의 렌더링 결과까지 확인해 절대 경로가 노출되는지 기록한다. 현재 코드는 예외를 로그에
   첨부하므로 파일 예외 메시지에 경로가 포함될 수 있다. 경로가 검출되면 LOG03과 함께 차이를
   기록한다.
   [기존 재시도 테스트](../../../backend/src/test/java/com/tripee/backend/admin/PhotoCleanupServiceTest.java)

## LOG05 업무 감사와 트랜잭션

- READY 게시를 성공시켜 `201`과 Location에서 리비전 ID를 확보한다. 별도 DB 연결에서 `PUBLISH` 감사가
  1건 늘었는지 확인한 뒤, 관리자 감사 조회에서 같은 이벤트의 행위자·도시·리비전·행위와 시각을
  대조한다.
- 독립 케이스에서 게시가 롤백되도록 주입하고 일반 게시본과 성공 감사 건수가 그대로인지 확인한다.
  오류 및 보안 이벤트는 각 기록 정책에 따라 확인한다. 비공개·물리 삭제 후에는 도시 식별값을 기준으로
  기존 감사 기록이 남는지 확인한다.
- 운영 환경에서 수집기가 중단된 시간을 포함해 업무 감사 이력의 보존 여부를 확인한다. 개인정보
  접속기록을 적용하는 범위에서는 별도 필수 필드·조회 권한·보유 기간도 검증한다.
  [게시 후 상태](test-case-execution-draft.md#publish-atomic) ·
  [개인정보 접속기록](korea-legal-security-test-review-2026-11-23.md#l06-개인정보-접속기록)

## LOG06 수집 장애·복구와 알림

- 스테이징에서 번호가 붙은 테스트 이벤트를 정상 연결 중 3건, 수집 연결을 잠시 중단한 동안 3건, 복구
  후 3건 발생시킨다. 수집된 번호와 시각을 대조해 지연·누락·중복을 측정하고, 버퍼가 있는 구성에서는
  복구 후 다시 수집되는 범위를 확인한다.
- R15의 5xx·사진 정리 실패·느린 응답에서 합의된 조건과 평가 시간에 맞춰 경보를 발생시킨다. 발생부터
  담당 수신, 조치, 해제까지 시각을 남기고 동일 장애의 중복 알림 횟수도 확인한다. 로그 조회 권한과
  보유 정책은 허가된 테스트 계정과 별도 테스트 데이터로 확인한다.
  [R15](test-case-execution-draft.md#r15-로그메트릭알림) ·
  [기록 보유·점검](korea-legal-security-test-review-2026-11-23.md#l07-기록-보유점검)

## LOG07 서비스 간 식별자 전파

서비스 분리 시 정상·실패 게시 요청을 서로 다른 식별자로 보내고 진입 서비스→의존 서비스 순으로
연결한다. 비동기 처리도 사용하면 같은 업무 이벤트의 ID와 소비자 기록을 대조한다. 승인된 추적
정책으로 실제 실패 구간과 재시도 횟수를 식별할 수 있어야 하며, 서로 다른 요청의 로그가 섞이거나
비밀값이 다른 서비스로 전파되면 실패다.
[MS08 분산 추적](msa-test-spec-draft.md#ms08-분산-추적과-장애-탐지)

## LOG08 재시작 후 장애 로그 보존

실제 배포와 같은 로그 전달·버퍼·중앙 저장소 구성을 격리된 스테이징에 준비한다. 승인된 수집 지연
상한, 허용 유실 범위, 보유 기간을 실행 기록에 적는다. 테스트에서 기대하는 장애 이벤트의 ID·발생
지점·시각은 중앙 저장소 바깥의 비교용 기록에 남긴다.

| 경우                            | 실행 절차                                                                                                                                                     | 중앙 저장소에서 확인할 결과                                                                                                     |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 중앙 저장 완료 뒤 서비스 재시작 | 게시 또는 의존 서비스 호출을 실패시키고 중앙 조회에서 해당 이벤트를 확인한다. 로그를 발생시킨 서비스 인스턴스를 교체하고 새 조회 세션에서 같은 ID를 검색한다. | 장애 전후 로그가 처음과 같은 ID·서비스·오류 분류로 조회된다. 정상 요청은 새 인스턴스의 기록으로 확인된다.                       |
| 로그 전달 중단 중 서비스 재시작 | 수집 연결을 끊고 식별 가능한 장애 이벤트를 발생시킨 뒤, 전달이 중단된 상태에서 서비스 인스턴스를 교체한다. 연결을 복구한다.                                   | 설정이 보장하는 미전달 기록이 기한 안에 재수집된다. 원본 ID 집합과 비교해 유실·중복을 기록하고, 허용 범위를 넘으면 실패다.      |
| 수집기 재시작과 전달 재개       | 앞선 시험과 별도 실행에서 수집기에 아직 전달 중인 이벤트가 있는 상태로 수집기만 재시작한다. 이미 저장된 이벤트와 재개 뒤 들어온 이벤트를 각각 검색한다.       | 저장 완료분은 계속 조회된다. 재전송분은 원본 발생 시각과 식별자로 찾을 수 있고, 중복이 장애 건수나 알림 집계를 부풀리지 않는다. |

시험 종료 시각까지 중앙 조회에서 찾은 ID와 비교용 기록을 대조한다. 증거로 재시작 전후 인스턴스 ID,
저장 완료 확인 여부, 이벤트별 발생·수집·조회 시각, 누락·중복 건수와 조회 결과를 남긴다. 보유 정책이
설정되면 만료 직전까지 조회되는지, 만료 후에는 해당 정책의 처리 결과와 일치하는지도 시험한다. 수집
지연·유실 기준 미정이면 관찰값을 남기고 합격 판정을 보류한다.

### 재시작 시험의 기록 예시

검색에는 요청 응답이나 테스트 수집기에서 얻은 ID를 넣는다.

| L08-A     | 수집 정상, 앱 인스턴스 교체 전    | 발생·수집 시각, 기존 인스턴스 ID, 재시작 전에 확인한 저장 기록. 새 조회 세션에서 재조회 |
| L08-B     | 수집 단절 중, 앱 인스턴스 교체 전 | 실제 trace ID, 연결 복구 시각, 재수집 시각. 승인된 지연·유실 기준과 대조                |

## LOG09 저장된 로그로 장애 원인 재구성

### 장애 분석에 필요한 기록

| 필드                  | 확인 내용                                                                                                                                               |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 발생 시각과 기록 주체 | UTC 발생 시각, 서비스·인스턴스·배포 버전으로 실패를 기록한 지점을 확인한다. 수집 시각이 있으면 발생 시각과 대조한다.                                    |
| 요청 및 이벤트 연결   | 요청 또는 trace ID를 남기고, 비동기 처리에는 이벤트 ID와 원래 작업을 연결할 정보도 남긴다. 여러 단계의 순서는 요청 간 관계와 시도 번호를 함께 사용한다. |
| 실패 작업과 오류      | 수행한 작업 또는 라우트, 호출 대상, 오류 코드 또는 예외 분류를 남긴다. 타임아웃과 연결 실패, 요청 거부를 구분할 수 있는지 확인한다.                     |
| 재시도와 최종 결과    | 재시도가 있는 경우 첫 호출을 포함한 시도 번호와 결과를 대조한다. 최종 성공·실패·처리 대기 또는 결과 미확정 상태를 기록한다.                             |

위 표는 필드의 의미를 정한다. 이름·형식·샘플링과 필수 기록 범위는 선택한 관측 설정과 내부 계약에
맞춰 확정한다. [LOG03 비밀정보 노출 검사](#log03-비밀번호토큰내부-정보-비노출)도 함께 적용한다.

### 진단 재현

1. 정상 공개 조회를 대조군으로 실행한다. 이어 승인된 테스트 대역으로 사진 제공자 응답 지연을 만들고,
   별도 실행에서 안전정보 조회 의존성을 일시적으로 사용할 수 없게 한다. 두 경우 모두 진입 서비스에
   비슷한 장애 응답이 돌아오는 구성이라면 각각의 내부 원인을 식별할 수 있는지 특히 확인한다.
   메시징을 쓰면 게시 커밋 후 읽기 모델 소비가 중단되는 경우도 추가한다.
2. 장애 주입 지점을 모르는 대응자 역할에 장애 시간대와 오류 응답의 요청 ID를 제공한다. 비동기 실패의
   경우 운영 경보에 포함된 이벤트 또는 업무 식별자를 제공한다. 대응자는 중앙에 저장된 로그에서 최초
   실패 서비스·작업·오류 분류, 후속 오류, 재시도 횟수, 최종 상태를 찾고 조회 근거를 남긴다.
3. 대응 결과를 별도로 기록한 장애 주입 위치, 요청·이벤트 기록, 필요한 경우 게시본의 실제 DB 상태와
   대조한다. 최초 실패와 상위 서비스의 후속 오류를 올바르게 구분하고, 최종 응답과 데이터 상태의
   차이까지 설명할 수 있어야 한다. 여러 요청을 합쳐 원인을 오판하거나 필수 기록 누락으로 결론을 낼
   수 없으면 실패다. 승인된 진단 시간 목표가 있으면 함께 측정한다.

예를 들어 LOG09의 서로 다른 실행에서 사진 의존 호출을 4초 지연시키고 호출 제한을 1초로 둔 경우와,
안전정보 의존 서비스 연결이 실패하는 경우를 비교한다. 첫 기록은 사진 조회 단계의 타임아웃, 두 번째
기록은 안전정보 조회 단계의 연결 실패에 대응해야 한다. 두 요청의 실제 ID를 분리하고 재시도 횟수는
해당 내부 계약과 대조한다. 4초·1초는 재현값이다.
