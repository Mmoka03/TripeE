## 읽는 방법

- **유효 분할**: 해당 조건만으로는 거부하지 않아야 하는 입력 또는 상태임. 다른 선행 조건을 모두
  충족해야 성공함.
- **무효 분할 / 제외 대상**: 입력 검증 항목에서는 계약상 거부해야 하는 입력임. 조회 항목에서는
  결과에서 제외할 데이터 상태도 포함하므로, 제외를 요청 오류로 해석하지 않음. 오류 상태·코드는 해당
  API와 검증 순서에 따라 달라지므로 실제 요청별로 확인함.
- **경계·대표값**: 각 분할의 대표와 경계 양쪽을 고르기 위한 후보임. 길이는 별도 표시가 없으면
  유니코드 코드 포인트 기준임.
- **기존 근거**: 정적으로 확인한 대표 테스트임. 해당 항목의 모든 경우를 이미 테스트했다는 뜻은 아님.
  `부분`은 일부만 확인한 경우, `추가 확인`은 기존 테스트 존재 여부를 아직 확정하지 않은 경우임.
- **우선순위**: P1은 인증·데이터 유실·공개 범위, P2는 일반 계약·입력 경계, P3은 AI 제공자 선정 후
  또는 운영 규모 확장 시 다룸.
- 테스트 계층: U=단위, M=MockMvc, P=격리 PostgreSQL 통합, E=실제 브라우저·서버 연동. 저장소를 목으로
  대체한 단위 테스트만으로 SQL·트랜잭션을 검증했다고 보지 않음.

- **계층·우선순위:** U·M / P2

## 7. 초안 적절성 평가와 수정 사항

아래는 초기 초안 평가와 보강 과정의 근거다. 현재 문서 전체의 재평가·남은 작업은
[테스트 안내의 재평가](README.md#2026-11-23-재평가), 경로별 연결과 미결정 계약은
[작업 연결표](api-operation-test-matrix.md)를 기준으로 한다.

**최초 초안은 요구사항 검토용으로 적절하지만, 그대로 실행할 수 있는 테스트 명세로는 부족했다. 이번
보강본은 우선순위가 높은 테스트를 구체화하는 설계 단계이며, 전체 테스트 완료나 배포 승인을 뜻하지
않는다.** 평가는 문서·소스·대표 테스트의 정적 검토에 한정한다. 이번 문서 수정에서는 테스트와
커버리지를 재실행하지 않았다.

### 요구사항 범위·추적

- **최초 초안 평가:** 주요 업무를 폭넓게 포함. 요구사항 ID가 있어 후속 관리에 유용
- **이번 보강:** 누락된 활동·사전·초안 생명주기·독립 게시를 아래에 추가
- **남은 한계:** [39개 작업 연결표](api-operation-test-matrix.md) 추가. 개별 assertion·실행 결과
  연결은 미완료

### 동등 분할·경계값

- **최초 초안 평가:** null/누락/빈 값, 최대값, 시간·소유권 분할은 적절
- **이번 보강:** JSON 타입과 URL 값 구분, 비일치 검색을 오류와 구분
- **남은 한계:** 한 항목의 여러 분할에 개별 ID가 필요. 모든 범위의 내부 대표값·경계 양옆을 확정하지
  않음

### 조건·조합·상태

- **최초 초안 평가:** 개별 값 중심. 복합 조건의 독립 검증과 전이 순서가 부족
- **이번 보강:** 조건·분기 후보, 결정표, 상태 전이 표 추가
- **남은 한계:** 실제 테스트와 조건별 실행 결과 연결은 후속 작업

### 기대 결과의 구체성

- **최초 초안 평가:** 일부 행은 “거부/롤백”만 있어 판정하기 어려움
- **이번 보강:** 상태·오류 코드, 저장 금지·변경 후 불변조건을 명시
- **남은 한계:** 경로별 오류 우선순위와 미확정 계약은 추가 합의 필요

### 기존 테스트 근거

- **최초 초안 평가:** 실제 테스트명을 제시하고 “부분”으로 제한한 점은 적절
- **이번 보강:** 검색어 1자 테스트와 롤백 검증의 한계를 재확인

### 실행 순서·재현성

- **최초 초안 평가:** P1 위험 우선, Clock·격리 DB 사용 방향이 적절
- **이번 보강:** 정상 기준 데이터, 실패 주입, 동시 시작 장벽·타임아웃, 완료 기준 제안
- **남은 한계:** 테스트 구현·실행 이력·실패 재현 자료는 별도로 필요

정정한 주요 사항:

  공급자와의 실제 통합만 P3로 남겼다.

### 평가 수준

아래 단계는 이 문서를 위한 내부 평가 기준이며 인증 등급이나 테스트 충족률이 아니다.

| 단계                     | 판단 기준                                                       | 현재 판정                                         |
| ------------------------ | --------------------------------------------------------------- | ------------------------------------------------- |
| 1: 항목 나열             | 기능·테스트 이름만 있음                                         | 해당 단계보다 발전함                              |
| 2: 요구사항 검토 초안    | 주요 유효/무효 분할, 경계, 위험, 기존 근거가 있음               | 최초 초안의 수준                                  |
| 3: 테스트 설계 초안      | 핵심 조건·결정표·전이·실패 후 상태까지 구체화                   | **이번 보강본의 수준. 우선순위별 구현 착수 가능** |
| 4: 실행·추적 가능한 명세 | API→분할→케이스→테스트 메서드→동일 커밋 실행 결과 연결          | 미달: 전체 연결·구현·실행 증거 필요               |
| 5: 지속 검증 체계        | 4단계와 함께 변경 영향, 결함 탐지력, 성능·운영 위험을 지속 관리 | 미달: 후속 자동화·운영 기준 필요                  |

실제 코드의 TDD 준수 수준·테스트 통과율·요구사항 충족률은 이 문서 점수로 대체할 수 없다. 특히 기존
코드를 위한 테스트 보강은 회귀 검증이며, 과거에 실패 테스트부터 작성했다는 증거가 되지 않는다.

각 테스트는 **정상 기준 데이터를 먼저 만든 뒤 한 조건만 바꾼다.** 다중 오류는 검증 순서 자체를
검사하는 별도 케이스로 분리한다. 분할 ID는 `요구사항-ID-EP번호`, 케이스 ID는 `요구사항-ID-T번호`로
부여한다. 무효 분할은 우선 누락→null→타입→형식→범위 순으로 구분하고, 같은 차원 안에서 겹치지 않도록
한다. 경계값은 해당 분할의 대표값 후보이지 별개의 기법 적용 완료 증거가 아니다.

예: P04 limit의 실행용 초안. 나머지 요청은 유효하고, 충분한 개수의 서로 다른 검색 결과를 준비한다.

| 분할 ID  | 분할 정의         | 케이스 ID·입력                     | 기대 결과                                   | 기존 확인                       |
| -------- | ----------------- | ---------------------------------- | ------------------------------------------- | ------------------------------- |
| P04-EP01 | 생략              | P04-T01: 파라미터 없음             | 200, 결과 최대 10개                         | 기존 기본값 테스트 있음         |
| P04-EP02 | 허용 정수 1~50    | P04-T02~06: 1, 2, 25, 49, 50       | 각 200, 충분한 결과가 있으면 정확히 limit개 | 양끝 1/50 성공은 추가 확인 필요 |
| P04-EP03 | 범위 아래 정수    | P04-T07~08: -1, 0                  | 400 `INVALID_QUERY`, 데이터 조회 없음       | 0은 기존 확인                   |
| P04-EP04 | 범위 위 정수      | P04-T09: 51                        | 400 `INVALID_QUERY`, 데이터 조회 없음       | 기존 확인                       |
| P04-EP05 | 빈 값·비정수 표현 | P04-T10~12: `""`, `"1.5"`, `"xyz"` | 각각 400 `INVALID_QUERY`, 데이터 조회 없음  | 기존 확인                       |

이 예시는 기본 정수 범위 기준이다. `+1`, `01`, 공백, 매우 긴 숫자, 중복 쿼리 키의 수용 정책은
명세·바인딩 규칙을 확인해 별도 확정한다. 코드가 현재 수용한다는 이유만으로 요구사항으로 고정하지
않는다.

## 9. 조건·분기 테스트 추가 초안

최종 판정의 참/거짓, 각 조건의 참/거짓, 한 조건이 판정에 미치는 독립적인 영향은 구분한다.
`A || B`에서 A가 참이면 B가 실행되지 않을 수 있으므로 B를 검사할 때는 A가 거짓이 되도록 준비한다.
중요한 복합 조건은 한 조건만 바꾸는 비교 쌍을 작성하되, 서로 종속되어 불가능한 조합은 이유와 함께
제외한다. 이를 자동으로 MC/DC 충족이라고 보고하지 않는다.

JaCoCo 분기는 바이트코드 기준 `if`·`switch` 실행 지표이며 예외 처리를 분기로 세지 않는다. 따라서
분기 수치와 별도로 예외·복구·업무 조합을 검증한다.
[JaCoCo Coverage Counters](https://www.jacoco.org/jacoco/trunk/doc/counters.html)

아래는 **보강 후보**이며 전부 미구현이라는 뜻은 아니다. 기존 테스트의 정확한 assertion을 연결한 뒤
부족한 케이스만 추가한다.

### B01 / C03·W03

- **계층·우선순위:** U·M / P1
- **대상 조건:** `DraftWriteValidator.objectFields`: 객체 여부 OR 필드 수 OR 필수 키 누락
- **추가할 입력·케이스:** 정상, 배열, 필드 수 부족/초과, **같은 필드 수에서 필수 키를 미지원 키로
  교체**
- **기대 결과·후조건:** 422 `VALIDATION_FAILED`; 마지막 조건까지 실제 도달. 상위 서비스에서는 저장
  호출 없음

### B02 / W04

- **계층·우선순위:** U / P2
- **대상 조건:** `positiveInt`: 정수 여부 OR int 표현 가능 OR 양수 여부
- **추가할 입력·케이스:** 1/최대 int, 소수·문자, 최대+1, 0/-1을 독립 준비
- **기대 결과·후조건:** 유효 값 통과, 각 오류 거부. 범위 오류가 타입 오류에 가려지지 않음

### B03 / W01

- **계층·우선순위:** U / P2
- **대상 조건:** `coordinates`: 위·경도 각각의 하한/상한
- **추가할 입력·케이스:** 한 축 0 고정, 다른 축 경계·범위 밖. 숫자 타입 오류도 한 축씩
- **기대 결과·후조건:** 각 축의 네 범위 분기와 형식 거부 확인, 유효 경계 허용

### B04 / W09

- **계층·우선순위:** U / P2
- **대상 조건:** `validate`: from 존재 AND until 존재 AND 종료≤시작
- **추가할 입력·케이스:** null/null, 시각/null, null/시각, 종료 직전/동일/직후, 다른 offset의 동일
  순간
- **기대 결과·후조건:** 한쪽 null 허용, 종료≤시작 거부; 마지막 조건 도달을 위해 양쪽 유효 시각 사용

### B05 / W05·W07

- **계층·우선순위:** U / P1
- **대상 조건:** `PublicationValidator`: checkedAt 존재 AND evidenceNote 존재
- **추가할 입력·케이스:** 출처 하나에 대해 두 필드의 4조합. 여러 출처 중 검토 완료 항목이
  처음/마지막에 있는 경우
- **기대 결과·후조건:** 둘 다 있어야 검토된 출처로 인정. 순서와 무관하게 하나라도 검토 완료면 해당
  출처 요건 충족

### B06 / A04

- **계층·우선순위:** U·P / P1
- **대상 조건:** `EditLockService.requireOwner`의 OR 조건들
- **추가할 입력·케이스:** 정상 대비 token null/blank/오류, 바인딩 없음, actor/창/바인딩 해시
  불일치를 각각 분리

  `EDIT_LOCK_EXPIRED`로 별도 검증

### B07 / A02·A03

- **계층·우선순위:** U·P / P1
- **대상 조건:** `withLease`, `heartbeat`, `release`

## 10. 결정표 테스트 초안

### 사진 권리 메타데이터 — B09 / M02

### 일반 게시와 안전 기반 충돌 — B11 / W06·W07

세션·편집권·초안 버전·요청 형식은 모두 유효하다. “일반 게시 위반”은 안전 기반 충돌 이외의 필수
콘텐츠·안전정보 검증 위반을 뜻한다. `-`는 그 행에서 결과에 영향을 주지 않는 값이다. 현재 구현의 오류
우선순위를 기초로 한 초안이며 정책 변경 시 명세부터 갱신한다.

## 12. 테스트로 전환할 때의 완료 기준

### 요구사항 추적

- **기록·완료 기준:** HTTP 작업·명세 절 → 요구사항 ID → 분할 ID → 케이스 ID → 테스트 클래스/메서드

### 케이스 상세

- **기록·완료 기준:** 선행 데이터·입력·고정 시각·예상 응답·DB/파일 후조건을 케이스별 기록
- **현재 상태:** 핵심 조건·결정표 구체화, 나머지는 후속 세분화

- **기록·완료 기준:** 같은 커밋의 단위·DB 통합 실행을 구분하고 합산 분기 보고서를 검토. P1 누락

- **현재 상태:** 이번 변경에서 측정하지 않음. 수치만으로 조건 조합 검증 완료 판단 금지

  저장

## 13. 보안 관점의 기존 테스트 평가

검토일: 2026-11-23. 기존 A01~A06·M01~M04·B06~B10·X06은 보안을 일부 다루지만, 보안 요구사항 전체를
검증하는 표는 아니었다. 아래는 소스와 테스트 assertion의 정적 확인 결과다. **보안 회귀 테스트의
기반은 있으나, 운영 보안을 충족했다고 판단할 증거는 부족하다.** 실행 결과를 새로 확인하거나 침투
테스트를 수행한 평가는 아니다.

판정에서 **기존 확인**은 해당 테스트 코드가 있다는 뜻이고, **보강 필요**는 일부만 검증한다는 뜻이다.
**미확인**은 검토한 범위에서 전용 테스트를 찾지 못한 경우이며 전체 저장소에 절대로 없다는 의미가
아니다. **정책 선행**은 기대 결과를 먼저 합의해야 하는 항목이다.

- 모든 관리자가 모든 도시를 관리하는 현재 정책에서는 “다른 관리자가 만든 도시”라는 이유만으로 접근을

  평문 비밀번호·토큰·비밀키 저장은 별도로 금지한다.

## 14. 보안 테스트 보강 초안

테스트 환경은 격리 PostgreSQL·임시 파일·가짜 계정·가짜 비밀값을 사용한다. 아래는 보안 요구사항과
합격 기준의 **계획**이다. 정책 선행 항목과 미구현 방어 기능은 테스트 추가만으로 해결되지 않으며 정책
확정·구현 후 통과해야 한다. OWASP API Security Top 10은 점검 누락을 줄이는 참고 분류이며, 아래 검증
항목이 OWASP 전체 준수를 인증하지 않는다.

### S01 / A01·X06: 기능 접근 통제(API5)

- **계층·우선순위·상태:** M·P / P1 / 보강 필요
- **준비·시나리오:** OpenAPI의 모든 관리자 작업에 익명/정상 관리자/만료 세션 적용. CSRF는 유효하게
  두어 인증 분기에 도달. CSRF 발급·로그인 예외 별도
- **기대 결과·후조건:** 보호된 작업은 익명 401·만료 401, 조회/쓰기/파일/외부 호출로 진행하지 않음.
  미지원 메서드는 계약대로 거부. 인증 예외가 다른 경로까지 확장되지 않음

### S02 / A01: 권한·세션 불일치

- **계층·우선순위·상태:** M / P1 / 정책 선행·미확인
- **준비·시나리오:** SecurityContext의 인증 주체만 존재, AdminSession 없음/다른 ID, 향후 일반 사용자
  역할 세션
- **기대 결과·후조건:** “인증된 관리자 세션의 두 신원이 일치해야 함”을 정책으로 확정한 뒤 보호 작업
  거부 검증. 테스트 주입 상태와 실제 생성 가능한 상태를 구분

### S03 / A01·A06: CSRF

- **계층·우선순위·상태:** M·P / P1 / 일부 기존 확인
- **준비·시나리오:** 인증 세션에 정상/누락/오류/다른 세션 토큰, 로그인 전 토큰의 로그인 후 재사용;
  POST/PUT/PATCH/DELETE 각각
- **기대 결과·후조건:** 정상만 진행, 잘못된 토큰은 403 `CSRF_INVALID`, 서비스 변경 없음. GET으로
  상태 변경 불가. 로그인·로그아웃도 적용

### S04 / A01·A02·A05: 세션 탈취·재사용

- **계층·우선순위·상태:** M·P·E / P1 / 보강 필요
- **준비·시나리오:** 로그인 전 세션 ID 재사용, 로그아웃 후 쿠키, 만료 직전/정확히 만료, 같은 계정의
  두 세션
- **기대 결과·후조건:** 로그인 전·로그아웃 후 ID로 관리자 접근 불가, 만료 복구 불가. 한 세션
  로그아웃 시 다른 세션·그 잠금 유지

### S05 / A01: 로그인 남용(API2·API6)

- **계층·우선순위·상태:** M·P·E / P1 / 정책·방어 구현 선행
- **준비·시나리오:** 동일 계정/여러 계정·동일/다른 클라이언트의 연속 실패와 정상 시도;
  존재/미존재/비활성 계정
- **기대 결과·후조건:** 임계 횟수·구간·키·복구 정책 결정 후 제한 및 우회 방지 검증. API 제한은
  계약상 429·Retry-After 확인. 에지 제한이면 응답 계약 별도 정의. 세 실패 응답에 계정 정보 없음

### S06 / A04·W04·M03: 객체 접근(API1)

- **계층·우선순위·상태:** M·P / P1 / 부분 기존 확인
- **준비·시나리오:** 도시 A의 토큰으로 B의 초안·사진·게시 요청, B의 항목/사진 ID를 A 저장에 삽입,
  다른 도시의 과거 리비전 요청
- **기대 결과·후조건:** 토큰·도시 소속 오류를 계약대로 거부, B와 A의 데이터·버전·공개 포인터·감사
  이력 불변. 전역 출처 공유는 허용 정책 유지

### S07 / C03·W03: 과다 필드·서버 값 변조(API3)

- **계층·우선순위·상태:** U·M·P / P1 / 보강 필요
- **준비·시나리오:** actorId, checkedAt, publishedBy, visibility, baseSafetyRevisionId, 임의 role 등
  경로별 쓰기 불가 필드 삽입
- **기대 결과·후조건:** 입력 스키마의 허용 필드 외 값은 400/422 등 명세대로 거부. 서버의
  작성자·확인일·버전 계산을 덮어쓰지 못함

### S08 / P01·M03·H01: 노출·캐시

- **계층·우선순위·상태:** M·P·E / P1 / 일부 기존 확인
- **준비·시나리오:** HIDDEN/초안/폐기/삭제/비공개 전환 후 공개 JSON·검색·사진 접근, 관리자/익명 교대
- **기대 결과·후조건:** 허용 공개 필드만 반환. 초안·암호 해시·원문 토큰·내부 저장 키 없음. API
  no-store, 이미지 캐시 정책 별도 확인. 프록시가 이전 관리자/공개 콘텐츠를 잘못 제공하지 않음

### S09 / P05·W10·H01: SQL 주입

- **계층·우선순위·상태:** U·M·P / P1 / 리터럴·계정 조회 주입 일부 확인·HTTP 확장 필요
- **준비·시나리오:** 검색·커서·로그인에 작은따옴표·주석·논리식 같은 문자열, ID에 비숫자. 정상
  `%`·`_` 리터럴 검색도 구분
- **기대 결과·후조건:** 바인딩된 데이터로 처리하거나 입력 오류로 거부. 무관한 행 반환·인증 성공·DB
  변경 없음. 서비스 목 대신 실제 PostgreSQL에서 검증

### S10 / M01·M02: 업로드 악용

- **계층·우선순위·상태:** U·M·P / P1 / 일부 기존 확인
- **준비·시나리오:** 허용 이미지/MIME 불일치/위장 SVG·HTML/손상 이미지/픽셀 폭증, `../` 포함 원본
  파일명, 위치정보 있는 이미지
- **기대 결과·후조건:** 허용 이미지 정규화, 임의 원본 파일명으로 파일 생성 불가, 허용 외 형식 거부.
  정상 업로드 결과의 EXIF 제거·정규화 크기·실제 이미지 디코딩 확인

### S11 / M04: 파일 접근·삭제 이탈

- **계층·우선순위·상태:** U·P / P1 / 읽기 일부 기존 확인·정리 보강
- **준비·시나리오:** DB storage key의 상대/절대 외부 경로, 외부 심볼릭 링크·중간 디렉터리 링크, 정리
  작업의 잘못된 키
- **기대 결과·후조건:** 읽기는 404, 정리는 외부 파일 삭제 금지. 테스트 전후 임시 외부 파일의 내용
  동일 확인. 링크 교체 경쟁은 별도 파일시스템 위협 검토 후 제한적으로 검증

### S12 / C03·M01·I01: 자원 고갈(API4)

- **계층·우선순위·상태:** U·M·E / P1 / 크기 일부 확인·총량 정책 선행
- **준비·시나리오:** multipart 파일/전체 요청 한도와 +1, 큰 JSON·깊은 중첩·큰 배열, 동시 업로드·AI
  호출
- **기대 결과·후조건:** HTTP 계층에서 크기 제한·복구 가능한 오류, DB/파일 불변. 동시 요청
  한도·큐·타임아웃과 자원 회수 검증. JSON 한도 및 초과 응답은 먼저 정의

### S13 / C04: 오류·로그의 비밀값

- **계층·우선순위·상태:** M·P / P1 / 응답 일부 확인·로그 미확인
- **준비·시나리오:** DB/파일/JSON/AI 예외에 가짜 비밀번호·CSRF·세션·잠금 토큰·키·SQL·경로를 포함
- **기대 결과·후조건:** 응답·응답 헤더·앱 로그·감사 JSON에 비밀값 미포함. traceId로 내부 원인 추적
  가능하되 사용자 데이터 전체 기록 금지. 예상치 못한 RuntimeException도 검사

### S14 / A01: HTTPS·쿠키·CORS(API8)

- **계층·우선순위·상태:** M·E / P1(배포 전) / 운영 정책·환경 검증 필요
- **준비·시나리오:** 운영 HTTPS 로그인, 신뢰/비신뢰 프록시 헤더, 같은 출처/임의 출처
  Origin·preflight
- **기대 결과·후조건:** 실제 Set-Cookie에 Secure·HttpOnly·합의된 SameSite, URL 세션 추적 금지.
  미허용 출처에 자격 증명 읽기 허용 금지. 신뢰 프록시만 원래 HTTPS 판단에 반영

### S15 / W10·I01: SSRF(API7)

- **계층·우선순위·상태:** P / P2 / 외부 수집 없음·회귀 테스트 미확인
- **준비·시나리오:** 출처/사진 URL을 루프백·사설 주소·리다이렉트 주소로 등록하되 격리 로컬 HTTP
  수신기를 사용
- **기대 결과·후조건:** 현재 URL은 메타데이터이므로 등록·조회·제안 요청이 URL을 가져오지 않음(수신
  횟수 0). 실제 주소 차단을 요구하지 않음. 향후 수집 추가 시 IP·DNS·리다이렉트 정책 별도 설계

### S16 / I02: 외부 결과 불신(API10)

- **계층·우선순위·상태:** U·P / P2 / 로컬 일부 확인·외부 제공자 결정 후 확장
- **준비·시나리오:** 가짜 출처·과대/비정상 출력, 공급자 오류, 본문 속 지시문, 시간 초과·취소 무시
- **기대 결과·후조건:** 구조·출처 제한 검증, 자동 DB 쓰기·도구 실행 없음, 공급자 오류/키 비노출.
  실제 제공자 연결 시 전송 필드 allowlist·비밀값 제외·취소 후 자원/비용 상한 검증

### S17 / DB·H01: 최소 권한·감사 변조

- **계층·우선순위·상태:** P / P1 / 메타데이터 권한 일부 확인·실행 보강
- **준비·시나리오:** 실제 앱 계정으로 금지 DDL·TRUNCATE·감사 UPDATE/DELETE·계정 권한 변경 시도
- **기대 결과·후조건:** 격리 DB에서 권한 거부·트랜잭션 rollback, 정상 API 필수 DML은 가능. 허용된
  감사 FK null 처리 등 시스템 동작과 직접 변조를 구분. 런타임에 관리자 계정/DDL 계정 사용 금지

### S18 / API 인벤토리(API9)

- **계층·우선순위·상태:** M·E / P2(배포 전 P1) / 정적 경로 비교 일부 확인
- **준비·시나리오:** OpenAPI 작업·실제 매핑 비교, 미문서화 관리/디버그 경로·TRACE·설정 파일 경로
  요청
- **기대 결과·후조건:** 배포된 모든 엔드포인트에 공개/인증 정책 분류. 미사용 관리·디버그 기능
  비노출, `.env`·설정·소스·스택 미반환. 인프라 전체 라우팅도 별도 확인

### S19 / CI·운영 공급망

- **계층·우선순위·상태:** CI·정적 검사 / P2(유출 P1) / 별도 검사 미확인
- **준비·시나리오:** Java/Node 의존성·컨테이너 취약점, 추적 파일·빌드 결과의 가짜 비밀키 검출, CI
  토큰 권한
- **기대 결과·후조건:** 잠금/해결 버전과 도구 결과 저장, 악용 가능성·심각도별 처리 기준 설정. 비밀키
  검출 시 차단, 실제 키 로그 출력 금지. 예외는 만료일·담당 기록

### S20 / 콘텐츠의 저장형 XSS

- **계층·우선순위·상태:** M·E / P2 / 프론트 렌더링 검증은 팀 담당과 연동 후 수행
- **준비·시나리오:** 제목·본문·출처·AI 결과에 HTML/스크립트·위험 URL을 저장 후 API/화면 조회
- **기대 결과·후조건:** JSON 응답은 계약상 타입 유지, API에서 임의 HTML 실행 응답 없음. 실제 화면은
  문자열 이스케이프·허용 링크 스킴 검증, 실행 없음

### 보안 테스트의 실행·판정 규칙

1. 인증 테스트는 CSRF를 유효하게, CSRF 테스트는 인증을 유효하게 준비해 앞선 필터에 가려지는 것을
   막는다. 필터 조합 자체의 오류 우선순위는 별도 케이스로 둔다.
2. 서비스·컨트롤러 직접 호출은 필터·쿠키·프록시 방어의 증거가 아니다. MockMvc는 실제
   SecurityFilterChain을 켜고, 쿠키 재사용·multipart 한도·CORS·TLS는 실행 서버/브라우저 계층까지
   확인한다.
3. 400/401/403/404 응답만으로 합격시키지 않는다. 무권한 작업의 저장·파일·외부 호출 없음과 정상
   사용자의 성공을 함께 확인한다. 공유 출처·전체 관리자 도시 접근 등 허용 정책을 임의로 제한하지
   않는다.
4. S05·S12·S14의 수치·배포 정책은 먼저 확정한다. 정책 미정·방어 미구현은 미실행/차단으로 보고하며
   “기능이 없으니 테스트 제외”로 완료 처리하지 않는다.
5. 이번 평가에서 보안 통과율·완성률은 산출하지 않는다. 위 분할을 개별 케이스로 확정하고 구현·실행
   증거를 연결한 뒤 계산한다. 운영 취약점 스캔·침투 테스트 결과와 단위/통합 보안 회귀 결과도
   구분한다.

우선순위는 **S01~S08 접근·인증 → S10~S13 파일·자원·정보 노출 → S17 DB 권한**, 배포 전 **S14·S18**
확인 순이다. SQL 주입·외부 연동·CI 점검은 해당 기능 변경과 병행한다. 테스트 설계 문서 수준은 기존
3단계를 유지하며, 보안 범위가 추가되었다고 실행·운영 증거가 갖춰진 4단계로 올리지 않는다.

보안 위험 분류는
[OWASP API Security Top 10 2023](https://owasp.org/API-Security/editions/2023/en/0x11-t10/),
HTTP·접근 통제·로그·CORS 점검은
[OWASP REST Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html)를
참고했다. SQL 주입·CSRF·XSS 등은 별도 검증 항목이며 2023 Top 10의 독립 항목과 일대일로 대응하지
않는다.

## 15. 실제 서비스 배포를 위한 테스트 범위와 준비 상태

작성일: 2026-11-23. 아래는 실제 배포 시 사용할 추가 명세 초안이다. 배포 환경 구축·테스트 실행 결과가
아니며, 기능 테스트와 14절의 보안 테스트를 통과한 뒤에도 별도로 확인해야 하는 운영 위험을 다룬다.

### 배포 스모크·실제 사용자 E2E

- **확인하는 문제:** 배포된 주소에서 주요 기능이 실제로 이어지는가
- **현재 프로젝트에서 필요한 이유:** CI의 MockMvc 검사는 DNS·TLS·프록시·브라우저·쿠키·실제 파일
  저장까지 검증하지 않음

### 설정·기동·상태 검사

- **확인하는 문제:** 올바른 프로필·권한으로 시작하고 준비된 인스턴스만 요청을 받는가
- **현재 프로젝트에서 필요한 이유:** 기본 프로필은 DB 자동 구성을 제외함. 단순 프로세스 기동
  성공만으로 운영 API 준비를 판단할 수 없음

### DB 초기 설치·버전 업그레이드

- **확인하는 문제:** 빈 DB와 기존 데이터가 있는 DB 모두 안전하게 설치·변경되는가
- **현재 프로젝트에서 필요한 이유:** 현재 `schema.sql`은 Compose의 최초 초기화용이고 JPA
  `ddl-auto: none`, SQL init `never`임. 버전별 마이그레이션 도구는 확인되지 않음

### 영속성·백업 복구

- **확인하는 문제:** 서버/디스크 교체 뒤 DB와 사진을 함께 되살릴 수 있는가
- **현재 프로젝트에서 필요한 이유:** Compose에 DB 볼륨은 있지만 앱·사진 배포 정의는 없음. 사진 기본
  경로는 실행 디렉터리 기준 로컬 파일

### 재배포·종료·롤백

- **확인하는 문제:** 요청 처리 중 교체와 실패 배포에서 데이터가 안전한가
- **현재 프로젝트에서 필요한 이유:** 세션·편집 토큰 바인딩은 인스턴스에 의존. 앱만 이전 버전으로
  바꿔도 DB가 호환된다는 보장은 없음

### 부하·순간 폭증·지속 부하

- **확인하는 문제:** 예상 트래픽에서 지연·오류·메모리·DB 연결이 감당 가능한가
- **현재 프로젝트에서 필요한 이유:** 이미지 변환·DB 잠금·AI 요청은 서로 다른 자원을 소비하며 단위
  커버리지로 용량을 판단할 수 없음

### 장애·회복

- **확인하는 문제:** DB·저장소·외부 서비스 중단 후 정상화되는가
- **현재 프로젝트에서 필요한 이유:** 실패 응답 외에도 연결 풀 회복·고아 파일·불완전 게시·정리 큐
  재시도 확인이 필요

### 관측·알림·운영 절차

- **확인하는 문제:** 장애를 감지하고 원인을 추적해 정해진 시간에 복구할 수 있는가
- **현재 프로젝트에서 필요한 이유:** 현재 빌드에서 Actuator/운영 메트릭 전용 의존성을 확인하지 못함.
  로그만으로 운영 대응이 충분한지 검증 필요

### 브라우저·모바일·외부 자원

- **확인하는 문제:** 실제 사용 환경에서 지도·사진·로그인이 동작하는가
- **현재 프로젝트에서 필요한 이유:** 프론트는 서버 연동 후 검증해야 함. 지도·외부 자원 차단·Safari
  세션도 API 단독 테스트로 확인할 수 없음

확인한 현재 준비 상태:

- `infra/compose.yaml`은 DB와 프로비저닝용 개발 구성이다. DB healthcheck의 `pg_isready` 성공은 앱
  계정 권한·스키마 버전·공개 API 준비 완료를 증명하지 않는다.
- Backend CI는 빌드·격리 PostgreSQL·MockMvc 응답 계약을 검사하며, 스테이징 배포·복원·부하·롤백
  단계는 확인되지 않았다.
- `tools/api-contract/live-public.test.mjs`의 `test:live`는 실제 HTTP 검사에 재사용할 수 있다. 다만
  PUBLIC/PREPARING 데이터가 없으면 상세 하위 테스트를 skip하므로, 배포 합격 판정에는 두 상태의 고정
  fixture와 skip 0 조건이 필요하다. 관리자 쓰기·브라우저 흐름은 별도다.
- 세션 저장소·사진 공유 저장소가 준비되지 않은 상태에서 다중 인스턴스·무중단 배포를 전제하지 않는다.
  초기 단일 인스턴스 운영도 재로그인·편집권 만료·저장된 초안 복구와 허용 중단 시간을 확인해야 한다.

| --------------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 배포 구조       | 단일/다중 인스턴스, 도메인, TLS 종료 위치, DB·사진 저장 방식, 앱 자원 한도                | 환경 의존 테스트 차단. 로컬 통과로 배포 합격 처리 불가                      |
| 서비스 용량·SLO | 동시 사용자·요청률·데이터 규모, API군별 p95/p99 지연·서버 오류율·지속 시간, 계측 지점     | 기초 측정은 가능하나 성능 합격 보류. 기대 4xx와 예상 밖 5xx/타임아웃을 구분 |
| 복구 목표       | RPO=허용 데이터 손실 시간, RTO=복구 시간, 백업 주기·보존 기간·대상·접근권한               | 복구 연습은 가능하나 목표 충족 판정 보류                                    |
| 배포 중단·호환  | 허용 중단 시간, 진행 중 요청 제한 시간, 세션 재로그인 정책, 이전 앱과 새 스키마 호환 범위 | 무중단·롤백 가능으로 판정 금지                                              |
| 운영 대응       | 오류율/지연/디스크/DB 연결/정리 큐 알림 임계·평가 시간·복구 판정·대응 담당                | 알림 시험의 전달·감지는 확인 가능하나 대응 목표 합격 보류                   |

숫자는 팀이 승인한 용량·비용·서비스 목표로 정하며 임의의 보편적 합격값을 적용하지 않는다. 각
실행에는
`케이스 ID / 커밋·아티팩트 해시 / 설정 버전 / DB 버전·스키마 버전 / 데이터 seed / 자원 / 시작·종료 시각 / 예상·실제 / 통과·실패·스킵·차단 / 로그·메트릭·화면 근거 / 담당`을
남긴다. 알림 전달 시험은 테스트 채널·수신자 합의 후 수행한다.

### 배포 전 검증표

아래 모든 항목의 현재 실행 상태는 **계획·미실행**이다. 기존 테스트 재사용 여부와 배포 환경의 실제
통과를 혼동하지 않는다. P1은 해당 단계의 필수 항목이며 R20은 배포 직후에 판정한다. P2는 해당
확장·연동 기능을 활성화하기 전에 실행한다. 비적용은 선택한 배포 구조·범위와 이유를 기록한 경우에만
허용한다.

### R01 아티팩트·설정·기동 / P1

- **선행 조건:** 실행 JAR 또는 이미지, 운영 상당 설정·비밀값 공급, 앱 계정
- **절차·대표 시나리오:** 동일 해시 아티팩트를 깨끗한 환경에서 기동. postgres 프로필 정상/누락, DB
  비밀번호 누락/오류, 저장소 쓰기 불가 각각 시험
- **합격 기준·증거:** 정상은 실제 DB API·사진 사용 가능. 잘못된 구성은 정상 서비스로 트래픽을 받지
  않음. 비밀값 없는 시작 로그·설정 식별자 기록

### R02 상태·라우팅 / P1

- **선행 조건:** 준비/생존 상태 검사 및 프록시 정책 구현
- **절차·대표 시나리오:** 기동 중→준비 완료→DB 단절→복구→종료 순으로 probe·외부 요청 관측
- **합격 기준·증거:** 준비 전·종료 중 인스턴스에 신규 요청 미전달. DB 장애 시 정책에 맞게 readiness
  반영. DB 장애만으로 생존 실패·무한 재시작 유발 금지. 관리 endpoint 민감정보 비노출(S14·S18)

### R03 HTTPS·프록시 스모크 / P1

- **선행 조건:** 스테이징 도메인·인증서·실제 프록시
- **절차·대표 시나리오:** 외부 네트워크에서 공개 조회·오류·로그인·파일 응답 검사, HTTP와 HTTPS·큰
  multipart·헤더 전달 시험
- **합격 기준·증거:** 인증서/호스트 검증·합의한 리다이렉트, Secure 쿠키·Location·캐시·본문 크기 계약
  유지. DB와 내부 관리 포트 비공개(S14)

### R04 최초 DB 설치 / P1

- **선행 조건:** 빈 격리 DB, 관리자/앱 권한 분리, 설치·seed 절차
- **절차·대표 시나리오:** 스키마·역할·기준 국가/태그·초기 관리자 생성 후 앱 기동, 절차 재실행
- **합격 기준·증거:** 앱 권한으로 전체 핵심 API 가능, 테스트용 계정·도시가 운영 seed에 혼입 안 됨.
  재실행은 명확한 no-op/안전 거부이고 데이터 손실 없음

### R05 기존 DB 업그레이드 / P1(스키마 변경 시)

- **선행 조건:** 버전별 변경·버전 기록·실패 복구 절차, 이전 버전 데이터
- **절차·대표 시나리오:** 이전 DB→대상 버전 적용, nullable·대량 행·제약 포함. 중간 실패·재실행·중복
  배포도 시험
- **합격 기준·증거:** 데이터/감사/권한 보존, 버전 기록 정확, 중간 상태로 앱 서비스 금지. DDL
  잠금·중단 시간 목표 충족. 최초 배포는 baseline 기록, 후속 변경 전에 반드시 적용

### R06 사진·DB 영속성 / P1

- **선행 조건:** 운영 상당 DB·사진 영속 볼륨, 고정 데이터·파일 해시
- **절차·대표 시나리오:** 도시·게시본·초안·사진 생성→앱 재시작→교체 배포→호스트 교체 상당 복원
- **합격 기준·증거:** DB 레코드·파일 해시·공개 사진·감사 유지. 실행 디렉터리 변경으로 파일 유실
  없음. 앱 비권한 사용자도 필요한 볼륨 접근 가능

### R07 DB+파일 백업·복원 / P1

- **선행 조건:** 백업 정책·복구 목표, 다른 격리 복구 환경
- **절차·대표 시나리오:** 공개/비공개/초안·사진·이력·정리 대기 데이터를 백업. 원본에 접근 못 하는
  환경에서 새 DB와 사진 복원
- **합격 기준·증거:** 레코드·관계·권한·사진 해시·공개 API 일치, RPO/RTO 충족. 백업 생성 성공만으로
  합격 금지. DB와 파일 시점 일관성 검증

### R08 종료·교체 배포 / P1

- **선행 조건:** 종료 유예·라우팅 제외·플랫폼 강제 종료 시간 결정
- **절차·대표 시나리오:** 조회·저장·게시·업로드·AI 처리 중 SIGTERM. 별도 시험에서 강제 종료 후
  재기동
- **합격 기준·증거:** 정상 종료는 유예 내 완료 또는 명확한 실패, 부분 게시 없음. 강제 종료 뒤 불완전
  데이터 없음·고아 파일 복구 경로 있음. 새 요청과 진행 중 요청을 구분하며, 브라우저에서 게시 결과를
  확인하지 못한 경우에는 커밋 전후를 나누어 검증한다.
  [R11-T05](test-case-execution-draft.md#r11-t05-게시-응답-유실과-재접속)

### R09 앱 롤백·DB 호환 / P1

- **선행 조건:** 이전 아티팩트·설정·복구 절차, 이전/새 스키마 호환표
- **절차·대표 시나리오:** 새 버전 배포·쓰기 후 결함 주입→트래픽 차단→이전 앱 복귀, 핵심 업무 재검사
- **합격 기준·증거:** 목표 시간 내 복구, 새 데이터 보존·구버전 읽기/쓰기 정상. 비호환 스키마에는
  승인한 복원 또는 전진 수정 경로를 검증한다. 배포 전부터 열린 탭을 확인하고, 혼합 버전을 사용하는
  구성에는 구·신 앱이 같은 전환기 스키마를 사용할 때의 검증을 추가한다.
  [R09 실행 절차](test-case-execution-draft.md#r09-롤백db-호환)

### R10 세션·편집권 재기동 / P1

- **선행 조건:** 단일 인스턴스 세션 유실/보존 정책 명시
- **절차·대표 시나리오:** 두 세션 로그인·편집·저장 후 앱 교체. 옛 쿠키/토큰 요청, 재로그인·잠금 만료
  후 초안 재개
- **합격 기준·증거:** 옛 인증 우회 없음, 저장된 초안 유지. 세션 유실 시 안내·재로그인 가능, DB에
  남은 잠금은 계약상 만료·재획득 가능. 미저장 입력 복구 정책도 화면에서 확인

### R11 실제 사용자 E2E·UAT / P1

- **선행 조건.** 스테이징에 연결된 관리자·공개 UI, 실제 PUBLIC/PREPARING 도시, 격리된 쓰기 fixture와
  관리자 두 계정을 준비한다.
- **실행 범위.** 로그인부터 초안·게시·공개 조회·비공개 전환까지 확인한다. 오래된 탭의 저장 충돌,
  독립 안전 게시와 재검토, 기존 관리자 세션 회수, 게시 응답 유실을 각각 실행한다.
- **합격 기준.** 브라우저·HTTP·DB 결과가 일치해야 한다. 관리자 게시가 출시 범위에 포함되면
  R11-T01~T05를 모두 기록한다. 필수 fixture·환경이 누락되면 해당 케이스를 차단으로 남긴다.
  [R11 실행 절차](test-case-execution-draft.md#r11-실제-사용자-흐름)

### R12 기준 부하 / P1

- **선행 조건:** 합의한 사용자·RPS·혼합비율·데이터/자원 규모
- **절차·대표 시나리오:** 공개 목록/검색/상세·관리자 저장·업로드를 분리 측정 후 혼합. 준비 부하 후
  목표 부하 유지
- **합격 기준·증거:** API군별 p95/p99·오류율·처리량 목표, DB 연결/락 대기·힙·CPU·디스크 한도 충족.
  평균만으로 합격 금지. DB·공개 포인터 무결성도 확인

### R13 순간 폭증·한계·지속 / P1(최소 용량), P2(확장)

- **선행 조건:** 중단 기준·부하 상한·관측 도구
- **절차·대표 시나리오:** 허용 상한까지 단계 증가·짧은 폭증·지속 부하 후 회복. 이미지·AI는 별도 비용
  제한
- **합격 기준·증거:** 제한 동작·큐 안정·부하 감소 후 정상화, 메모리/스레드/커넥션/디스크 무한 증가
  없음. 실행 시간과 목표를 기록. 운영에 한계 부하 직접 적용 금지

### R14 의존 장애·자동 회복 / P1(DB·파일), P2(AI 활성화)

- **선행 조건:** 장애 주입 가능한 격리 환경
- **절차·대표 시나리오:** DB 연결 중단/재시작·풀 고갈, 저장소 읽기전용/가득 참, 공급자 timeout·오류
  후 복구
- **합격 기준·증거:** bounded timeout·정상 오류, 연결/자원 회수·서비스 회복, 부분 쓰기·비밀정보 노출
  없음. 제한된 재시도로 장애 증폭 방지. 파일·DB 원자성은 X04~X05 연계

### R15 로그·메트릭·알림 / P1

- **선행 조건:** 수집·대시보드·알림 경로·담당 확정
- **절차·대표 시나리오:** 5xx·느린 쿼리·디스크 부족·정리 작업 실패 유도→탐지→대응→복구
- **합격 기준·증거:** 목표 시간 내 감지·알림·복구 확인, 동일 요청 추적 가능·비밀값 없음(S13). 알림
  중복 폭증/복구 누락 없음. 현재 traceId의 응답·로그 연결 범위도 실제 확인

### R16 정리 배치·보존 / P1

- **선행 조건:** 삭제/정리 주기·보존 범위·시계 설정
- **절차·대표 시나리오:** 참조/미참조 사진·실패 작업 생성, 프로세스 중단·재기동과 다음 배치 실행
- **합격 기준·증거:** 참조 파일 보존, 미참조 작업만 완료·실패 재시도, 큐 적체 탐지. 복구된 과거
  백업의 참조와 최신 파일 삭제가 충돌하지 않도록 복원 절차 확인

### R17 모바일·호환·사용성 / P1(지원 범위)

- **선행 조건:** 지원 브라우저 목록, 프론트 실연동, 실제 HTTPS
- **절차·대표 시나리오:** macOS Safari·Chrome 및 iPhone Safari에서 검색·사진·로그인·오류·세션 만료.
  느린 네트워크·지도 자원 차단 시험
- **합격 기준·증거:** 터치/키보드·입력/오류 안내·재로그인·재시도 가능, 화면이 성공으로 오표시하지
  않음. 지도 공급자 실제 origin 키 제한·사용 조건 확인

### R18 다중 인스턴스 / P2(선택 시 배포 전 P1)

- **선행 조건:** 공유 세션/파일 또는 명시한 세션 정책, LB·정리 배치 정책
- **절차·대표 시나리오:** A에서 로그인/잠금·업로드 후 B로 요청, 인스턴스 제거, 중복 배치·혼합 버전
  실행
- **합격 기준·증거:** 인증·토큰 바인딩·사진 접근 일관, 경쟁 게시/정리 안전. sticky session만으로
  인스턴스 장애 복구를 입증하지 않음. 단일 구성은 사유 기록 후 비적용

### R19 외부 서비스·기능 비활성화 / P1(비활성 경로), P2(실제 연결)

- **선행 조건:** 지도·AI 제공자/키·쿼터·지원 범위 결정
- **절차·대표 시나리오:** AI 미설정/키 오류/쿼터/timeout, 지도 실패에서 사용자 흐름 확인
- **합격 기준·증거:** 현재 AI 미설정은 502 `AI_UPSTREAM_ERROR`, 자동 저장 없음. 비활성 기능 안내와
  나머지 API 정상. 제공자 연결 뒤 실제 sandbox 통합·전송 데이터·요금 상한 검증(S16)

### R20 배포 후 스모크·중단 판단 / P1

- **선행 조건:** 아티팩트 ID·모니터링·중단/롤백 기준·담당 확정
- **절차·대표 시나리오:** 배포 직후 공개 읽기·로그인·미인증 차단·기준 이미지 조회, 안정 관찰. 쓰기
  검증은 스테이징 우선
- **합격 기준·증거:** 배포 대상 해시 일치, 핵심 응답·오류율·지연 목표. 실패 시 배포 중단·담당
  통지·R09 실행 판단. 운영 쓰기가 필요하면 승인된 테스트 리소스·정리 절차만 사용

### 핵심 케이스의 상세 절차 예시

**R07-T01 — 백업을 새 환경에 복원**

1. 도시·일반 게시본·안전 게시본·수정 중 초안·감사·현재 공개 사진·비공개 보존 사진·정리 대기를
   생성한다. ID·포인터·관계 수·파일 해시의 기준 manifest를 만든다.
2. 스케줄러·업로드·게시·삭제를 포함한 쓰기를 멈추고 진행 중 요청을 배출한 일관된 시점을 만든다. DB
   백업과 사진 snapshot을 같은 복구 집합으로 기록한다. 무중단 snapshot을 선택하면 대신 사용하는 시점
   일관성 보장 절차를 검증한다.
3. 원본 DB·볼륨에 접근하지 못하는 새 환경에 백업·역할/권한·사진·설정 참조를 복원한다. 비밀값은 백업
   평문 복사 대신 승인한 공급 경로를 사용한다.
4. **사진과 DB의 복구 집합 검사가 끝나기 전 정리 배치를 실행하지 않는다.** 앱 계정으로 관계·공개
   포인터·파일 해시·게시 사진 접근·비공개 거부를 확인한다.
5. 로그인·새 초안 저장·감사 추가와 정리 재개를 확인한다. 데이터 기준 시점부터의 손실을 RPO, 복구
   시작부터 검증 후 서비스 재개까지를 RTO와 비교한다.

합격: 기준 집합의 참조 파일 누락·부적절한 공개·감사 유실이 없고 승인된 복구 목표 이내다. 손상·누락
백업의 감지와 다른 백업으로의 재시도는 R07-T02로 별도 기록한다. 실행 중인 PostgreSQL 데이터
디렉터리를 단순 복사한 것을 검증된 백업으로 취급하지 않는다.

**R08-T01 — 게시 중 정상 종료**

1. 충분한 콘텐츠·사진·근거를 가진 초안, 정상 관리자 세션·편집권을 준비하고 공개/초안/감사 기준
   상태를 기록한다.
2. 게시 요청이 실행 중인 것을 관측 가능한 장벽으로 확인하고 라우팅 제외와 SIGTERM을 적용한다. 앱
   종료 유예·LB drain·플랫폼 강제 종료 시간을 기록한다.
3. 클라이언트 응답, DB commit/rollback, 종료 로그·시간을 수집한다. 요청 성공이면 게시·감사·잠금
   해제가 함께 반영되어야 한다.
4. 응답을 받지 못했다면 재기동 후 조회로 commit 여부를 판정한다. 응답 유실을 rollback으로 가정하거나
   게시 POST를 무조건 재시도하지 않는다. 부분 상태가 없어야 한다.
5. 별도 R08-T02에서 강제 종료를 시행해 DB 복구·파일 잔여·정리 재개를 확인한다. 정상 종료의 합격을
   강제 종료까지 확대하지 않는다.

**R09-T01 — 데이터 변경 뒤 이전 앱 복귀**

1. 이전 앱 N-1, 새 앱 N, 적용할 스키마의 읽기/쓰기 호환표와 아티팩트 해시를 준비한다. 파괴적 변경이
   있으면 유지보수·전진 수정·백업 복구 중 사용할 경로를 먼저 정한다.
2. 스테이징에 N을 배포하고 새 콘텐츠 저장·게시·사진 등록을 수행한다. 장애 판정 조건을 주입해 배포
   중단을 확인한다.
3. 호환 가능한 경우 트래픽을 배출하고 N-1로 복귀한다. 새 버전에서 쓴 데이터·사진·이력 조회와 새
   저장·로그인을 수행한다.
4. 호환 불가이면 이전 앱을 억지로 실행하지 않는다. 정한 복구 경로를 연습하고 그동안의 쓰기 손실·중단
   시간을 기록한다. DB 복원은 최신 쓰기를 잃을 수 있어 RPO와 함께 판단한다.

합격: 재개 후 정상 업무·무결성이 유지되고 중단/복구 목표를 충족한다. JAR 교체만 성공한 것으로 롤백
합격 처리하지 않는다.

**R12-T01 — 목표 트래픽의 핵심 API 혼합 부하**

1. 운영 예상 도시·콘텐츠·사진 수와 별도의 성장 규모 데이터 집합을 준비한다. 조회/검색/관리자
   저장/업로드 비율·동시 세션·테스트 길이·자원 한도를 기록한다.
2. 준비 부하와 측정 구간을 분리한다. 읽기와 쓰기를 먼저 개별 측정하고 혼합 부하를 적용한다. 같은
   잠금 토큰을 여러 사용자처럼 공유해 비현실적 409만 발생시키지 않는다.
3. API군별 p95/p99, 예상 밖 5xx·timeout, 성공 처리량, DB 연결·대기·느린 쿼리, 힙·CPU·디스크 및 파일
   증가량을 수집한다. 느린 응답 때문에 실제 송신률이 목표보다 낮아졌는지도 확인한다.
4. 종료 후 서버가 기준 상태로 회복하는지 확인하고, 완료된 쓰기 수·감사·공개 포인터·정리 큐를
   대조한다. 목표값 미정이면 기준 측정으로만 보고한다.

성능 도구는 k6/JMeter 등으로 별도 선택할 수 있다. 현재 저장소에 도구·스크립트를 추가하거나 부하를
실행한 것은 아니다.

## 18. 실제 검증 절차와 상세 케이스 연결

테스트를 작성하거나 수동 실행할 때 아래 연결을 따라 준비 데이터와 정확한 요청값을 확인한다. 각 표
항목에 여러 값이 있으면 값마다 독립 케이스로 실행한다. 정상 요청을 먼저 확인하고 검증할 조건 하나만
바꾼다.

| 이 문서의 항목         | 상세 명세의 케이스            | 구체적으로 추가한 내용                                                                  |
| ---------------------- | ----------------------------- | --------------------------------------------------------------------------------------- |
| C01~C04                | F01~F04·F12                   | bigint 최대/overflow·JSON 파손·동일 키 수의 필수 필드 교체·ETag별 상태와 코드           |
| P01~P08                | F05~F09·F25                   | 노출 상태별 fixture·검색 길이와 결과 순서·태그 기존/신규 연결·안전 시각 경계            |
| A01~A06                | Q01~Q03                       | T0+3599/3600/3601 세션, +299/+300 잠금, 동일 계정 두 세션, 장벽을 이용한 실제 DB 경쟁   |
| D01~D05                | F10~F14·F27                   | 도시 생성·커서2/2/1 페이지·HTTP 조건부 변경·삭제/감사/파일 후조건·실패 주입             |
| W01~W12                | F15~F28·Q04~Q05               | 좌표·텍스트 실제 경계·초안 JSON·출처 검토·게시 가능한 데이터·안전 충돌/재검토 순서      |
| M01~M04·I01~I02·H01    | F29~F34                       | 실제 파일·MIME·픽셀·크기·AI 자료당/합계 한도·시간 초과·게시 이력과 삭제 후 감사         |
| B01~B12·결정표·X01~X13 | 상세 명세 3·6절               | 단락 평가 조건을 분리하는 입력, 권리8조합·게시 충돌, 속성/페어와이즈/변이 관측 방법     |
| S01~S20                | 상세 명세 4절                 | 원문 토큰·다른 도시 ID·SQL/파일/HTML 입력·HTTP Origin·앱 계정 권한 거부·비밀값 sentinel |
| R01~R20                | 상세 명세 5절 및 이 문서 16절 | 기동/장애 주입·백업 이후 쓰기·재배포 데이터·구체적 연습 부하·배포 후 스모크             |

상세 명세의 HTTP-OK/HTTP-ERR/NO-WRITE/SAVE-ONCE/PUBLISH-ATOMIC을 공통 assertion 묶음으로 사용한다.
실패 후 DB 비교는 요청 트랜잭션 종료 뒤 새 연결에서 수행한다. 저장소 목 검증만으로 SQL·rollback·파일
영속성이 확인됐다고 보고하지 않는다.

정적 재확인으로 기대값을 더 구체화한 부분:

- 안전정보 공개 상태 SQL은 `effective_from > CURRENT_TIMESTAMP`이면 UPCOMING,
  `effective_until <= CURRENT_TIMESTAMP`이면 EXPIRED다. 따라서 시작 시각과 정확히 같으면 CURRENT,
  종료와 정확히 같으면 EXPIRED다. P08의 종료 포함 정책은 이 구현을 근거로 상세 F25에 명시했으며 계약
  확정 여부도 검토한다.
- 해당 SQL의 시간은 DB의 트랜잭션 시각이다. Java Clock을 고정한 것으로 DB 시각까지 고정했다고
  판단하지 않는다. 같은 DB 트랜잭션의 CURRENT_TIMESTAMP로 정확한 경계를 준비한다.
- 유효한 ID·텍스트·파일 크기의 검사를 통과하는 것과 실제 요청 전체가 성공하는 것을 구분한다. 예를
  들어 최대 bigint라도 리소스가 없으면404이고, 정확10MiB라도 이미지가 파손되어 있으면 업로드 성공
  대상이 아니다.
- R/S 항목의 요청 제한·JSON 깊이·부하 시간 등 정책 미정 수치는 상세 명세에서 **정책
  후보/연습값**으로 표기한다. 이를 승인된 운영 기준이나 통과 결과로 취급하지 않는다.

## 19. 국내 법령에 따른 추가 검증

2026-11-23 기준 현행 법령 검토와 L01~L17 케이스는
[국내 법령 개인정보·보안 검증 추가안](korea-legal-security-test-review-2026-11-23.md)에 정리한다.
적용 근거·조건과 구체적인 시나리오를 함께 확인한다.

추가 우선 항목은 관리자 비활성화 후 기존 세션 회수, 업무 감사와 별도인 개인정보 접속기록·권한 변경
기록, 개인정보 파기와 백업 복원, 외부 지도·AI·클라우드 처리/국외 이전, 유출 확정·가능성 및 침해사고
대응이다. 개인정보 처리 해당 여부와 조항별 적용 조건을 확정한 뒤 케이스를 승인하며, 모든 웹사이트에
동일한 보유기간·위치정보 동의·ISMS-P 인증을 요구하지 않는다. 현재 L 항목은 계획 상태이며 법령 준수
확인 결과가 아니다.

## 우선 실행할 테스트 묶음

1. **P1 인증·동시성**: A01~A05의 세션·잠금 만료와 소유권, 실제 DB 경쟁·롤백을 분리하여 확인함. 고정
   `Clock`과 Testcontainers를 사용하고 시간 경계에 sleep을 사용하지 않음.
2. **P1 초안 원자성**: C03·D03·D05·W03~W08·M03~M04에서 한 조건씩 잘못된 요청을 만들고 상태 코드뿐
   아니라 초안·게시 포인터·출처 확인 시각·감사 이력·파일 정리 작업이 변하지 않았는지 검사함.
3. **P2 입력 경계**: P03~P06·D02·W01~W02·W09~W10의 유효 양끝과 바로 바깥을 매개변수 테스트로 작성함.
   의미가 다른 null·누락·빈 값을 같은 케이스로 취급하지 않음.
4. **계약과 브라우저**: C04의 미검증 상태와 공개 응답 비노출을 OpenAPI 자동 검증에 추가하고,
   프론트엔드 연동 후 E2E를 별도 작성함.
5. **P2/P3 AI**: 입력·결과 검증 및 제공자 미설정 오류는 P2로 지금 검증하고, P3인 실제 공급자가
   결정되면 타임아웃·오류·응답 유효성·입력 유출 정책을 해당 구현과 통합 검증함.

## 미확정 사항과 사용 제한

- 이 명세는 우선순위가 높은 대표 분할을 정리한 초안이며, 26개 경로·39개 HTTP 작업의 모든
  요청·응답·예외 조합을 열거한 것은 아님. OpenAPI의 작업별 명세와 대조해 확장해야 함.
- `violations`의 422 응답 상세, 429 요청 제한, AI 제공자 동작은 현재 미완료 또는 결정 대기 항목임.
  기대 테스트를 만들기 전에 정책·구현의 차이를 확인함.
- 문서의 API 정책, OpenAPI, DB 제약과 현재 구현이 다를 때 실제 응답만 기준으로 정답을 정하지 않고
  팀과 계약을 확인함.
- 단위·통합 테스트의 존재나 커버리지는 테스트 우선 개발 과정의 증거가 아님. 새 작업은 실패 테스트 →
  최소 구현 → 리팩토링 순서와 실행 결과를 기록함.
