# MSA 전환 테스트 명세 초안

[테스트 문서 안내](README.md)

검토일 2026-11-25. 현재 백엔드는 단일 Spring Boot 애플리케이션이다. 아래 도시 관리·공개
조회·사진·인증은 테스트에서 경계를 설명하기 위한 분리 후보이며, 서비스 구성과 통신 방식은 향후
설계에서 결정한다.

기존 명세의 R09(구·신 버전 호환), R14(의존 장애), R15(관측), R18(다중 인스턴스), X07(HTTP 계약)은

실패·이벤트 재처리 검증은 아래 케이스에서 다룬다. 현재 CI 범위는 Spring 앱과 격리 PostgreSQL 통합 및
그 응답의 공개 API 계약 검사다.

## 적용 조건과 공통 준비

- 서비스 분리 후보마다 API 호출 방향, 데이터 쓰기 권한과 원본 소유자, 요청 성공이 보장하는 상태,
  장애 시 응답과 책임을 기록한다. 비동기 방식을 도입하면 이벤트 스키마·중복 식별자·엔터티별 순서
  또는 버전 기준·반영 기한·복구 절차도 명시한다.
- [공통 준비 데이터](test-case-execution-draft.md#1-공통-준비-데이터와-판정-규칙)의 관리자 A1·A2,
  CP(PUBLIC), CR(PREPARING), CH(HIDDEN), READY를 재사용한다. CP의 이전 게시본에는 `기존 공개 이름`,
  새 초안에는 `MSA 게시 이름`을 넣는다. 사진은 초안 전용과 공개 연결을 구분해 실제 서버가 저장한
  파일의 해시를 기록한다. 도시·사진·안전 버전 ID와 ETag는 생성·조회 응답에서 얻는다.
- 네트워크·권한·데이터 소유권은 서비스 프로세스를 각각 띄워 실행한다. 실제 DB 및 파일 저장소는
  격리하고, 채택한 경우 브로커·게이트웨이·인증도 검증에 포함한다. 장애를 가하기 전 같은 구성에서
  정상 대조군을 먼저 실행한다. 통신 대역은 타임아웃과 응답 오류를 재현하는 경우에 사용한다.
- 번호는 분리 시 검증을 위한 케이스 ID다. 적용되는 MS01~MS09를 출시 전 필수로 제안한다. 현재 단일 앱
  배포에는 분산 전용 케이스를 비적용으로 기록한다. 선택한 설계에 필요한 계약·환경·기준값이 없으면
  차단으로 기록한다. 현재 케이스 상태는 계획이다.

## MS01 데이터 소유권과 모듈 경계

- **준비와 실행.** 첫 분리 후보가 공개 조회라면 도시 관리와 공개 조회의 앱 계정·데이터 접근 권한을
  기록한다. 현재 코드에서는 각 모듈이 참조하는 저장소와 SQL을 목록화한다. 분리 환경에서 관리자가
  편집권과 최신 ETag로 CP의 초안을 저장하고, 공개 조회 계정의 업무 조회와 쓰기 권한을 해당 권한
  명세에 대조한다.
- **합격 기준.** 원본 초안은 승인된 쓰기 경로에서만 갱신된다. 조회 전용 계정의 원본 쓰기 시도는
  거부되며 감사·도시·초안 상태가 그대로다. 서비스별 저장소가 있다면 공개 조회는 승인된 조회
  인터페이스 또는 자기 읽기 모델을 사용한다. 별도 DB 구성 여부와 실제 권한 근거를 기록한다.
- **실제 연결 검증.** 각 서비스에서 사용한 DB·스키마·계정과 TLS를 확인하고, 별도 DB가 있는 경우 한쪽
  DB를 중단했을 때의 영향과 복구를 증명한다.
  [DDB01 연결 검증](distributed-db-cloud-test-spec-draft.md#ddb01-서비스별-db-대상계정tls) ·
  [DDB02 풀 고갈과 장애 격리](distributed-db-cloud-test-spec-draft.md#ddb02-연결-풀-고갈과-부분-장애-격리)

## MS02 서비스 간 계약과 독립 배포

- **준비와 실행.** 소비자(호출하는 쪽)·제공자(응답하는 쪽) 버전을 고정한다. 내부 계약에 따라
  정상·미존재·오류 응답을 실제 제공자에서 검증한다. 예를 들어 사진 조회에는 권한 있는 기존 자산과
  없는 자산을, 게시 이후에는 `201`의 `Location`을 사용한 같은 리비전의 재조회를 넣는다. HTTP
  경계라면 타입·nullable·오류 코드·필요한 헤더를 케이스별로 기록한다.
- **버전 조합.** 기준 조합 N/N과 전환 중 발생하는 N-1 소비자/N 제공자 및 N 소비자/N-1 제공자를
  실행한다. 새 제공자의 선택 필드 추가에 대한 이전 소비자의 처리와, 새 소비자가 이전 응답의 선택
  필드 없이 동작하는지 확인한다. 이벤트를 사용하면 읽고 쓰는 스키마 버전도 이 조합에 포함한다.
- **합격 기준.** 지원되는 모든 버전 조합에서 계약과 후조건이 일치하고, 게이트웨이를 거친 기존 공개
  API의 경로·상태·헤더도 기준을 충족한다. 혼합 운용을 지원하지 않는 조합은 배포 순서와 라우팅으로
  발생하지 않는지 확인한다. [기존 HTTP 계약 검증](api-operation-test-matrix.md#출시-필수-검증-연결)

## MS03 부분 장애와 재시도

- **준비와 실행.** 게시·사진·AI 등 분리한 호출에서 성공, 연결 실패, 서비스 오류, 제한 시간 초과를
  독립 실행한다. 1차 재현값으로 요청 전체 3초, 시도당 최대 1초, 읽기 최대 2회(첫 호출 포함), 테스트
  제공자 지연 4초를 사용할 수 있다. 승인된 재시도 대상과 지연 상한을 요청 기록과 대조한다. 이 수치는
  검증용 예시이며 실제 계약과 운영 목표를 별도로 기록한다.
- **합격 기준.** 호출 전체가 합의한 시간·시도 횟수 내에 종료된다. 필수 제공자 장애에서 성공 응답이나
  불완전한 공개 상태가 생기면 실패다. 게시 결과가 불명확하면 먼저 상태를 재조회한다. 중복 방지
  계약이 있는 쓰기는 같은 요청 식별자로 재시도해 한 번의 결과만 확인한다. 선택 기능인 AI가 장애여도
  일반 초안 저장과 편집권이 유지된다. 장애 해제 후 정상 요청 성공과 자원 회복을 확인한다.
  [응답 유실 실행 절차](test-case-execution-draft.md#r11-t05-게시-응답-유실과-재접속)
- **장애 격리.** 호출량 제한이나 회로 차단기를 채택한 경우 느린 제공자 방향의 대기열·동시 호출이
  설정한 상한을 지키는지 확인한다. 장애 중 승인된 거부 응답, 의존하지 않는 경로의 응답, 복구 뒤 시험
  호출과 정상 요청의 재개를 기록한다.

## MS04 게시·비공개 전환의 정합성

1. CP에서 READY를 바탕으로 새 게시를 준비한다. A2가 안전정보를 독립 게시한 뒤 A1이 이전 안전 기반의
   일반 초안을 게시한다. `409 SAFETY_CHANGED`와 현재 안전 버전 ID를 대조하고 일반 게시본이 바뀌지
   않았는지 확인한다. 현재 버전 ID 응답의 구현 차이는 G10으로 추적한다.
   [Q04](test-case-execution-draft.md#q04-안전-수정본의-저장충돌재검토) ·
   [G10](api-operation-test-matrix.md#g10)
2. 최신 안전 기반을 재검토하고 일반 게시를 진행한다. 동기 경계라면 필수 처리 완료 전 실패를 주입해
   부분 성공이 없는지 확인한다. 이벤트 경계라면 원본 쓰기 커밋 전 실패와 커밋 후 읽기 모델 처리
   중단을 분리한다. 첫 경우에는 성공 게시가 보이지 않아야 한다. 두 번째 경우에는 승인된 지연 정책
   안에서 최종 공개본으로 수렴하고 게시 리비전과 업무 감사가 각각 1건만 추가되어야 한다.
3. 익명 목록·상세·검색·사진을 각각 조회한다. 이전 공개본이 허용되는 구간에도 초안과 미확정
   사진·안전정보를 노출하면 실패다. 비동기 처리로 기존 공개 API의 성공 의미나 노출 시점이 달라지면
   계약 승인을 먼저 받는다.
4. 편집권을 다시 획득해 최신 도시 ETag로 CP를 비공개로 전환한다. 성공 직후와 읽기 모델·파일 서비스
   장애 중 익명 목록·검색에 대상이 없어야 하며, 직접 상세·사진 URL도 비노출 정책을 충족해야 한다.
   오래된 공개 데이터가 뒤늦게 반영돼 비공개 도시가 다시 노출되는지 확인한다.
   [공개 조회와 비공개 전환](test-case-execution-draft.md#r11-t01-관리자-게시와-공개-조회)

## MS05 이벤트 중복·역순·재처리

이벤트나 비동기 작업 큐를 채택할 때 실행한다. 각각 새 fixture에서 같은 이벤트 ID를 두 번 전달하고,
별도 실행에서 같은 도시의 새 버전 다음에 이전 버전을 전달한다. 테스트에서는 버전 순서를 기록하며
DB에서 자동 발급된 ID만으로 전달 순서를 가정하지 않는다. 소비자가 반영한 직후 처리 확인을 기록하기
전에 중단시키고 재시작한다. 복구 불가 입력은 승인된 격리 절차로 보내고 뒤이은 정상 이벤트까지
처리되는지 확인한다.

최신 공개 포인터·검색 결과·사진 연결이 이전 버전으로 돌아가면 실패다. 중복 전달에도 게시·감사·파일
변경 같은 업무 효과는 각각 한 번만 발생해야 한다. 처리된 이벤트 ID·버전·재전달 횟수와 복구 전후
상태를 남긴다.

## MS06 서비스 호출 권한과 사용자 세션

- **준비와 실행.** 승인된 호출 주체와 권한이 없는 테스트 주체를 준비한다. 인증 정보 누락·만료·권한
  불일치에서 내부 업무 요청이 거부되는지 확인한다. 분리 경계가 관리자 경로에 있으면 정상 세션과
  CSRF·편집 토큰 대조군, 세션 회수 뒤 이전 탭 요청, 별도 관리자 세션의 정상 요청을 각각 실행한다.
- **합격 기준.** 승인된 서비스만 지정된 작업에 접근한다. 관리자 권한·편집권 판정 결과는 호출 경계를
  지나도 일치한다. 거부된 요청은 도메인 데이터나 성공 감사 이력을 만들지 않으며, 접근 거부 기록은
  정책에 따라 남긴다. 익명 조회·오류 응답·로그·추적에서 사용자 세션 원문, 편집 토큰, 내부 저장
  경로를 노출하지 않는다. [세션 회수](test-case-execution-draft.md#r11-t04-기존-관리자-세션-회수)

## MS07 서비스별 배포와 롤백

- **준비와 실행.** 연결된 서비스는 이전 버전으로 유지한 채 대상 하나만 N으로 교체한다. 전환 도중
  정상 읽기와 쓰기를 실행하고 MS02의 호환 조합을 확인한다. 마이그레이션을 적용한 구성에서는 N으로
  쓰기를 한 뒤 N-1로 돌아가 이전 앱에서 그 데이터와 사진을 조회한다. 이벤트 사용 시 대기 중인
  메시지가 있는 상태에서도 검증한다.
- **합격 기준.** 합의한 범위 안에서 조회·쓰기가 이어지며 새로 쓴 데이터·세션 정책·게시 이력·사진
  해시가 보존된다. 롤백 불가능한 조합은 승인된 복원 또는 전진 수정 절차로 검증하고 사용 불가 시간과
  데이터 손실을 측정한다. [기존 롤백·DB 호환](test-case-execution-draft.md#r09-롤백db-호환)

## MS08 분산 추적과 장애 탐지

- **준비와 실행.** 게이트웨이를 쓰는 구성에서는 게이트웨이부터, 그 외에는 최초 진입 서비스부터 정상
  게시와 실패 게시 각각의 추적을 모은다. 메시징을 쓰면 소비자 처리까지 같은 업무 흐름으로 연결한다.
  사진 제공자 지연이나 소비 지연을 주입한 뒤 의존하지 않는 공개 경로도 함께 측정한다.
- **합격 기준.** 요청 식별 정보로 문제 응답과 실제 실패 구간·재시도·최종 결과를 찾을 수 있고 승인된
  알림이 담당자에게 전달된다. 계약에 합의한 공개 API의 오류율·지연 기준과 이벤트 반영 기한을
  검사한다. 증거에는 토큰과 비밀번호를 남기지 않는다.
  [기존 관측 테스트](test-case-execution-draft.md#r15-로그메트릭알림)
- **장애 증거 검증.** 진입·의존 서비스와 수집기의 재시작 전후에 운영과 같은 중앙 로그 조회 경로에서
  장애 기록을 다시 찾는다. 장애 주입 지점을 모르는 대응자가 저장된 기록으로 최초 실패 위치와
  재시도·최종 상태를 재구성한 결과를 남긴다.
  [LOG08 로그 보존](logging-test-spec-draft.md#log08-재시작-후-장애-로그-보존) ·

## MS09 저장소 분리 전환과 복구

서비스별 데이터나 읽기 모델을 이전하는 경우 적용한다. CP·CR·CH와 사진·게시·안전·감사 기록을 포함한
기준 스냅샷을 만든다. 쓰기를 유지하는 전환이라면 스냅샷 이후 CP의 새 게시와 또 다른 공개 도시의
비공개 전환을 실행하고 새 저장소에서 두 변경을 확인한다. 쓰기 정지를 사용하는 전환이라면 스냅샷부터
전환까지 쓰기가 실제로 차단되는지 확인한다. 읽기 모델 재구축을 지원하면 중간에 중단 후 재개해 같은
검사를 반복한다.

공개 목록·검색·상세·사진 해시, 안전 버전, 관리자 게시·감사 조회를 원본과 대조한다. 전환
누락·중복·비공개 데이터 재노출이 없어야 하며, 차이가 있는 동안에는 트래픽을 전환하지 않는다. 복구
시에는 재개 시점과 처리하지 못한 변경 범위를 기록해 승인된 RPO·RTO와 비교한다.
[기존 백업·복원](test-case-execution-draft.md#r07-백업복원)

## 서비스 분리 시나리오의 입력과 기대 결과

실제 서비스가 여러 개로 배포되면 아래 예를 팀이 정한 엔드포인트와 이벤트 스키마에 대응시킨다. N과
N-1은 새 버전·이전 버전을 가리키는 이름이다. E1·E2 역시 이벤트 ID를 하드코딩하는 값이 아니라 시험
기록에 붙이는 별칭이다.

| 케이스                         | 먼저 준비할 값과 순서                                                                                                                  | 결과 비교                                                                                                     |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| MS01·MS02 데이터 소유권과 계약 | 공개 서비스는 조회 전용 역할로 실행한다. 기존 사진 1개와 존재하지 않는 사진 ID를 준비하고, 지원하는 N/N·N-1/N·N/N-1 조합으로 요청한다. | 원본 DB의 쓰기 거부와 불변, 각 조합의 응답 계약, 같은 리비전과 사진이 조회되는지 확인                         |
| MS03 부분 장애                 | 첫 요청은 정상, 다음 요청은 연결 실패, 또 다른 요청은 4초 지연으로 실행한다. 연습용으로 호출 전체 3초, 읽기 최대 2회를 적용할 수 있다. | 응답 분류, 시도 횟수, 최종 상태. 필수 저장이 실패했으면 성공 감사 0건, 독립 경로의 정상 응답 확인             |
| MS04 안전 충돌                 | A1이 안전 기반 S0으로 READY와 안전 수정본을 저장한다. A2가 독립 안전 게시로 S1을 만든 뒤 A1이 같은 일반 초안을 게시한다.               | `409 SAFETY_CHANGED`, 일반 게시 포인터 불변, 응답의 현재 안전 버전은 실제 S1과 일치. 필드가 빠지면 G10에 기록 |

| MS06 권한                      | 정상 호출 주체, 허용 역할이 없는 테스트 주체, 만료된 테스트 자격 증명으로 각각 요청한다.                                               | 승인된 주체의 정상 처리, 거부 요청에서 업무 데이터와 성공 감사 불변                                           |
| MS07·MS09 전환과 복구          | 후보 서비스 하나만 교체한다. 스냅샷 뒤 CP의 새 게시와 별도 공개 도시의 비공개 전환을 1회씩 실행한다.                                   | 구·신 버전 전환 뒤 파일 해시·일반 및 안전 리비전·감사가 맞고 실제 적용된 변경이 빠지지 않는지 확인            |
| MS08 장애 원인                 | 정상과 실패 요청의 실제 ID를 각각 보관한다. 중앙 조회에서 장애를 확인한 뒤 서비스 또는 수집기를 재시작한다.                            | 재조회한 장애 기록과 실제 주입 지점이 일치하는지 확인한다. LOG08·LOG09의 근거를 첨부                          |

상태 코드와 수치가 아직 합의되지 않은 배포 기능은 승인된 계약을 기다린다. 같은 API라도 게이트웨이의
타임아웃과 내부 서비스의 오류가 다를 수 있으므로 어느 계층의 기대값인지 기록한다.

## CI와 출시 확인

1. 서비스별 CI에는 자기 모듈 회귀와 변경한 내부 계약 및 권한 검사를 넣는다. 여러 버전이 함께
   동작하는 배포라면 실제 버전 조합별 검사 결과를 남긴다.
2. 통합 환경에는 실제 개별 아티팩트를 배치해 MS03~MS09의 적용 케이스를 실행하고 기존 API 계약과
   공개·관리자 브라우저 흐름을 다시 확인한다. 동일한 앱 복제본 사이의 검사는 R18 결과로 기록한다.
   MS08의 합격 증거에는 재시작 후 중앙 조회 결과와 원인 분석 기록을 포함한다. 서비스별 DB 또는
   클라우드 인프라를 쓰는 구성은 DDB·CL 케이스의 실제 환경 검증도 포함한다.
   [분산 DB·클라우드 실행 증거](distributed-db-cloud-test-spec-draft.md#실행-증거와-출시-판정)
3. 케이스 ID, 서비스별 커밋·아티팩트 해시, 계약·스키마 버전, fixture, 실패 주입 지점,
   HTTP·이벤트·저장소 증거와 판정을 기록한다. 택한 구성에 해당하는 필수 케이스가 스킵되거나 차단되면
   출시 판정을 보류한다.
