## 적용 범위와 공통 준비

- 서비스별 아티팩트·배포 설정 버전, 접속 대상의 DB 식별자와 역할, 앱·마이그레이션 계정, 네트워크·TLS
  설정, 저장소와 소유자를 기록한다. 비밀번호와 토큰은 버전·식별 정보로만 남긴다.
- 도시 관리와 공개 조회를 분리하는 경우를 예로 든다.
  [공통 fixture](test-case-execution-draft.md#1-공통-준비-데이터와-판정-규칙)의 공개 도시 CP·준비 중
  CR·비공개 CH, 관리자 A1과 READY를 준비한다. CP의 기존 공개본·새 초안·안전 버전·사진 해시와 감사
  건수를 기준값으로 저장한다. 해당 기능이나 구성의 이름과 경로는 실제 설계를 따른다.
- 격리 스테이징의 정상 대조군에서 API와 저장소 상태를 먼저 확인한다. 구성이나 장애 요인을 하나씩
  바꿔 실험하고, 서로 영향을 주는 조합은 별도 실행으로 표시한다. 강제 전환·격리는 스테이징의 승인된
  장애 조치 절차로 수행한다.
- 시험 데이터와 측정 구간은 재현용이다. 서비스별 연결 예산, 복제 허용 지연, RPO·RTO, 전환 관찰 시간,
  오류율·지연·비용 한도는 배포 기준으로 확정한다. 채택한 기능에 필요한 환경이나 합격 기준이 없으면
  해당 케이스를 차단으로 기록한다. 사용하지 않는 복제·확장·저장 방식 등은 비적용 사유를 기록한다.

## 분산 DB 연결과 데이터 정합성

### DDB01 서비스별 DB 대상·계정·TLS

1. 각 서비스의 실제 런타임 연결에서 DB·스키마·현재 역할과 TLS 검증 설정을 확인한다. 예를 들어
   PostgreSQL에서는 `current_database()`, `current_schema()`, `current_user`로 연결 대상을 확인할 수
   있다. 같은 서비스의 정상 API를 호출해 해당 연결에서 기대한 데이터가 조회·변경되는지 대조한다.
2. 독립 실행마다 DB 이름, 스키마, 접속 계정, 인증서 신뢰 설정을 하나씩 잘못 지정한다. 시험용 서비스
   계정으로 승인된 읽기·쓰기와 역할 정책상 허용되지 않는 다른 서비스 저장소 접근을 각각 확인한다.
3. 정상 구성만 해당 업무를 수행해야 한다. 오설정으로 다른 DB에 성공하거나 TLS 검증 없이 연결되면
   실패다. 잘못된 구성은 준비 상태와 라우팅에 반영되어야 하며, 진단 기록에는 대상 식별 정보와 오류
   분류를 남긴다. [MS01 데이터 소유권](msa-test-spec-draft.md#ms01-데이터-소유권과-모듈-경계)

### DDB02 연결 풀 고갈과 부분 장애 격리

스테이징 풀을 4개로 작게 설정하고 테스트 요청으로 연결 4개를 잡은 뒤, 다섯 번째 요청에서 대기 제한과
응답을 관찰한다. 예시 제한은 1초이며 실제 정책으로 대체한다. 이후 연결을 반환하고 같은 서비스의 정상
요청이 다시 성공하는지 확인한다. 별도 DB를 쓰는 두 서비스가 있다면 한 DB만 단절하고 다른 DB를 쓰는
독립 경로에서도 대조군을 실행한다.

연결 대기·시간 초과·성공 건수가 설정과 맞고 요청이 무기한 대기하지 않아야 한다. 실패 요청의 부분
변경이 없어야 하며, 복구 후 풀 사용량이 기준 범위로 돌아와야 한다. 각 DB 접속 대상에 대해 서비스별
최대 복제본 수 × 풀 상한을 합산하고 운영·배치 연결을 더해 연결 예산과 비교한다. 자동 확장 시 실제
연결 피크도 측정한다. [R14 의존 장애](test-case-execution-draft.md#r14-의존-서비스-장애)

### DDB03 읽기 복제본의 쓰기 차단과 지연

읽기 복제본을 쓰는 구성에서만 실행한다. 복제 지연을 재현할 수 있는 격리 환경에 CP의 기존 공개본을
준비하고, 새 게시와 HIDDEN 전환을 별도 실행으로 커밋한다. 지연 구간에 관리자 재조회·공개
목록·검색·상세·사진을 반복 호출해 각 요청이 실제로 향한 DB와 관찰한 리비전을 기록한다. 복제본
연결에서는 읽기 성공과 쓰기 불가를 확인한다.

관리자 저장 직후 읽기는 승인된 일관성 계약을 지켜야 한다. 일반 공개본의 이전 버전이 허용되는 구간은
합의된 지연 안에 새 버전으로 수렴해야 한다. 비공개 전환이나 권한 회수처럼 오래된 값이 접근 통제를
무효화할 수 있는 경로는 지연 중에도 정책을 지켜야 한다. 임계 초과 시 승인한 주 서버 읽기·오류
응답·트래픽 제외가 작동하는지 확인한다.
[MS04 게시 정합성](msa-test-spec-draft.md#ms04-게시비공개-전환의-정합성)

### DDB04 주 DB 장애 조치와 쓰기 결과 확인

주 DB 장애 조치를 지원하는 구성에서 선택한 방식으로 전환한다. 정상 읽기와 쓰기가 있는 상태에서 주 DB
변경을 일으킨다. 커밋 전 연결 종료와 커밋 후 응답 유실을 서로 다른 도시에서 실행한다. 응답 타임라인,
새 연결이 선택한 대상, 기존 풀 회복 시점, 정상 쓰기 재개 시점을 기록한다.

전환 뒤 쓰기는 승인된 새 주 DB에서만 일어나야 한다. 커밋 전 실패는 폐기된 변경과 성공 감사 이력
부재를 확인하고, 응답을 받지 못한 쓰기는 재조회로 결과를 확인한다. 같은 게시가 반복되어
리비전·감사·파일 변경이 중복되면 실패다. 잃거나 누락된 확정 쓰기와 복구 소요 시간을 승인된 RPO·RTO에
대조한다. [게시 응답 유실](test-case-execution-draft.md#r11-t05-게시-응답-유실과-재접속)

### DDB05 서비스별 스키마 변경과 롤백

이전 버전의 서비스와 DB fixture를 준비한 뒤 새 스키마를 적용한다. 구·신 앱이 함께 운영되는 경우 해당
조합에서 각각 조회·저장을 확인한다. 마이그레이션에 중간 실패를 주입하고 재실행해 버전 기록과
데이터가 일치하는지 확인한다. 마이그레이션 전용 계정과 앱 계정이 각자의 권한으로만 동작하는지도
검증한다.

다른 서비스의 독립 DB는 영향을 받지 않아야 한다. 새 버전이 쓴 리비전과 감사 기록을 기존 서비스 또는
승인된 복구 경로에서 조회한다. 비호환 변경은 트래픽 전환 차단과 복원·전진 수정 절차를 실제 운영
순서대로 검증한다. [MS07 서비스별 배포](msa-test-spec-draft.md#ms07-서비스별-배포와-롤백)

### DDB06 여러 저장소에 걸친 쓰기와 재처리

게시 원본 DB가 커밋된 뒤 공개 조회용 DB 반영을 중단한다. 반대로 원본 커밋 자체가 실패하는 경우도
실행한다. 이벤트를 쓰는 구성에서는 같은 이벤트를 두 번 처리시키고, 이벤트 없이 동기 호출하는
구성에서는 승인된 재조회·복구 경로를 실행한다.

원본 저장 결과와 공개 API의 결과가 승인된 성공 의미에 맞아야 한다. 복구 후 공개
목록·상세·검색·사진이 같은 게시 버전을 가리키고, 성공 리비전과 감사 이력은 각각 한 건이어야 한다.
실패한 초안이 노출되거나 비공개가 취소되어 보이면 실패다.
[MS04 게시 정합성](msa-test-spec-draft.md#ms04-게시비공개-전환의-정합성) ·
[MS05 이벤트 재처리](msa-test-spec-draft.md#ms05-이벤트-중복역순재처리)

### DDB07 DB·사진·이벤트의 함께 복원

선택한 백업·시점 복원 방식으로 DB별 백업과 사진의 대응 시점을 기록한다. 이벤트로 읽기 모델을
구축한다면 다시 읽을 위치나 마지막 적용 버전도 기록한다. 기준 시점 뒤 CP의 새 게시와 별도 도시의
비공개 전환을 발생시키고, 복원은 원본과 격리한 환경에서 수행한다.

복원 기준의 공개 포인터·안전 버전·사진 해시·감사 이력이 일치해야 한다. 읽기 모델을 복구할 때는 기준
이후 변경을 정책에 따라 적용하고 중복·참조 누락·비공개 재노출을 검사한다. 저장소 간 시점 차이로 배포
기준을 충족하지 못하면 트래픽을 차단하고 차이와 실측 RPO·RTO를 기록한다.
[R07 백업·복원](test-case-execution-draft.md#r07-백업복원)

## 클라우드 배포와 운영

### CL01 네트워크 경로·DNS·TLS 검증

승인된 출발 위치에서 공개 HTTPS→게이트웨이 또는 로드밸런서→서비스→DB·저장소 경로를 확인한다. 사설로
지정된 서비스·DB에는 공개 경로에서 접근이 거부되어야 한다. 내부 서비스 이름 해석 실패와 잘못된
인증서가 있는 경우를 각각 재현한 뒤 복구한다. DNS 결과·연결 실패 위치·TLS 검증 결과와 정상 업무의
재개 시간을 기록한다. [R03 HTTPS·프록시](test-case-execution-draft.md#r03-https프록시)

### CL02 서비스 계정과 자격 증명 교체

실제 실행 역할로 앱을 기동해 허용된 DB와 사진 저장소만 사용 가능한지 확인한다. 채택한 방식에 따라 DB
자격 증명 또는 서비스 역할의 인증 정보를 회전시키고, 기존 연결·신규 연결·이전 자격 증명 만료를
구분해 요청한다. 교체 뒤 정상 처리, 만료된 자격 증명 거부, 준비 상태와 로그 비노출을 확인한다. 교체
시 허용 중단 시간과 실패 복구 경로도 대조한다.
[LOG03 비밀정보 비노출](logging-test-spec-draft.md#log03-비밀번호토큰내부-정보-비노출)

### CL03 클라우드 사진 저장소와 정리 작업

객체 저장소나 공유 볼륨을 채택한 경우, 인스턴스 A로 업로드하고 B에서 정상 조회한 뒤 A를 교체한다.
게시 전·후·비공개 전환 후의 동일 사진에 대해 관리자와 익명 요청을 각각 검사한다. 별도 케이스에서
저장소 거부·읽기 오류를 격리 조건으로 재현해 불완전한 업로드의 레코드나 파일이 정상 자료로 보이지
않는지 확인한다. 파일 해시·권한·참조 유지·정리 재시도와 완료를 근거로 남긴다.
[R06 영속성](test-case-execution-draft.md#r06-db사진-영속성) ·
[R16 파일 정리](test-case-execution-draft.md#r16-파일-정리-배치)

### CL04 점진 배포·준비 상태·롤백

신규 버전의 준비 전·준비 완료·종료 중에 각각 요청을 보내 트래픽 대상과 처리 결과를 기록한다. 일부
트래픽에 먼저 배포하는 방식이라면 신규 버전에서 승인된 중단 기준을 넘는 오류를 유도해 확대가
중단되는지 확인한다. 기존 버전으로 복귀한 뒤 공개 조회·관리자 세션·게시 결과·사진 해시를 확인하고,
전환 중 받아들인 쓰기의 결과와 중단 시간을 기록한다.

## 로컬에서 풀 고갈 재현

현재 단일 PostgreSQL 구성에서 먼저 DDB02의 풀 대기와 연결 반환을 검증할 수 있다. 새 테스트의 Spring
컨텍스트에 다음 값을 적용한다. Testcontainers가 제공하는 앱 계정과 JDBC URL을 사용한다.

| Spring 설정                                   | 재현값        |
| --------------------------------------------- | ------------- |
| `spring.datasource.hikari.maximum-pool-size`  | `4`           |
| `spring.datasource.hikari.connection-timeout` | `1000` 밀리초 |

1. 테스트 앱이 실제 사용 중인 `DataSource`에서 연결을 하나 빌려 `SELECT 1`을 실행하고 닫는다. 정상
   응답이 확인되면 연결 네 개를 같은 풀에서 빌려 모두 유지한다.
2. 별도 작업으로 다섯 번째 연결을 요청한다. 설정한 대기 제한에서 획득이 실패하는지 확인한다. 테스트
   작업 자체의 종료 제한은 예를 들어 5초로 둬 무한 대기를 막는다. 원인과 실측 대기 시간을 기록하고,
   정확히 1,000ms에 끝난다고 가정하지 않는다.
3. 유지한 연결 하나를 닫고 새 연결에서 `SELECT 1`을 실행한다. 시간 초과된 대기 작업은 종료되어
   있어야 하며, 새 연결의 정상 쿼리는 성공해야 한다. 실패해도 `finally`에서 남은 연결을 모두
   반환한다.
4. API까지 확인할 때는 별도 실행에서 정상 요청을 확인한 뒤 고갈 상태에서 다시 요청한다. 실제
   라우트의 오류 매핑과 상태 불변을 단언한다. 이 로컬 시험은 해당 풀을 쓰는 앱에서의 결과로
   기록한다. 독립 서비스의 장애 격리는 두 서비스를 띄워 대상 DB 하나만 끊는 케이스로 실행한다.

## 실행 증거와 출시 판정

1. CI에서는 채택한 배포 정의의 검증, 권한과 네트워크 설정의 검토, 실제 DB를 쓰는 서비스 통합과
   마이그레이션 회귀를 연결한다. 배포 후보의 아티팩트와 스테이징에서 쓴 설정의 버전을 맞춘다.
2. 스테이징에서는 DB별 실제 대상·계정·TLS, 오류·복구 타임라인과 DB 커밋·감사·사진 후조건을 확인한다.
   클라우드에 설정한 라우팅·권한 교체·스케일링·장애 조치도 해당 구성에서 시험한다. 각 케이스에 적용
   여부와 사유, 후보 버전, 장애 지점, 관측값, 기대 결과와 판정을 기록한다.
3. 적용된 DDB·CL 케이스의 실패·스킵·차단이 있으면 해당 배포 구간의 출시 승인을 보류한다. 배포
   직후에는 승인된 읽기 중심 스모크와 지표로 트래픽 확대를 결정한다.
   [배포 판정 기준](test-equivalence-partitions-draft.md#17-배포-검증-순서와-합격-기준)
