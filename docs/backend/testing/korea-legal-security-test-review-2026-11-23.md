## 2. 현재 코드에서 확인한 개인정보 처리 후보와 공백

- `admin_account`의 login_id·display_name·password_hash, 감사 스냅샷의 관리자 ID/이름은 실제
  개인과의 결합 가능성을 확인해야 한다. 해시·숫자 ID라고 자동 익명정보가 되는 것은 아니다.
- `AdminSessionService.login`은 계정 활성 상태를 검사하지만, 기존 세션의 후속 요청마다 DB의
  is_active를 다시 검증하는 동작은 검토한 코드에서 확인하지 못했다. **로그인 후 계정 비활성화 시
  기존 세션·잠금도 차단되는지**가 추가 핵심 테스트다.
- 기존 audit_event는 도시 생성·변경·게시 이력이다. 개인정보 조회·다운로드의 접속지·처리
  대상·수행업무를 모두 남기는 법정 접속기록의 완전한 대체물로 확인되지 않았다.
- 감사 보존·관리자 삭제는 FK RESTRICT와 스냅샷 구조의 영향을 받는다. 도시 삭제 후 이력 유지 요구와
  별개로 개인정보의 항목별 보유 근거·기간·파기 방식이 필요하다.
- `frontend/.env.example`과 MapView의 기본 지도 스타일은 `tiles.openfreemap.org`를 사용한다.
  브라우저의 실제 요청에서 IP·Referer·타일 좌표 등 외부 전송 항목을 조사해야 한다. 외부 도메인
  사용만으로 국외 이전 해당 여부·수탁 관계를 확정하지 않는다.
- 최근 본 도시 ID와 관리자 시연 데이터는 localStorage를 사용한다. 서비스 실연동 시 실제 관리자
  입력·토큰이 데모 저장소에 잔류하는지 확인해야 한다. 클라이언트 내부 저장만으로 전부 서버
  수집이라고 단정하지 않는다.

위 코드는 사실 확인 근거이며, 아래 L 항목의 적용·미구현 범위는 테스트로 다시 확인한다.

## 3. 추가 검증 항목

**P1**은 개인정보를 실제 처리하는 서비스 공개 전에 적용 판정과 이행이 필요한 제안 우선순위다.
**조건부**는 해당 기능·사업 형태·규모에 해당할 때 활성화한다. 기술 테스트와 운영 절차·문서 검토를
함께 사용한다. 각 항목의 세부 실행값은 프로젝트용 제안이며 법이 특정 HTTP 코드·DB 구조·도구를
지정했다는 뜻이 아니다.

### 처리 범위·권한·인증

#### L01 처리 목록·최소 수집

- **근거·연결 항목:** 보호법2·15·16 / S08·S13
- **시나리오·검증 방법:** 테스트 관리자 `legal-test-a`·가짜 IP·테스트 인물 사진을 사용해
  로그인→편집→게시→오류. DB·로그·파일·HAR·localStorage·백업의 저장/전송 항목을 목록화
- **합격 기준·증거·우선순위:** 항목별 목적·처리 근거·대상·수신자·기간·위치·삭제 방법 기록.
  주민번호·전화번호 같은 불필요한 필드나 비밀값의 추가 저장 없음 / P1

- **근거·연결 항목:** 보호법15·22·30·31 / R11

- **합격 기준·증거·우선순위:** 방침과 실제 처리 일치, 책임/고충 창구 운영. 동의 근거일 때 필요한
  항목·목적·기간·거부 관련 고지·증거 확인. 모든 처리에 동의 팝업을 요구하지 않음 / P1

#### L03 계정 회수·최소 권한

- **근거·연결 항목.** 고시 5 / S01·S02·Q02. 브라우저 확인은
  [R11-T04](test-case-execution-draft.md#r11-t04-기존-관리자-세션-회수)에서 수행한다.
- **절차.** A1·A2를 각자 로그인시키고 A1의 편집권과 기존 세션을 확보한다. 관리 절차로 A1 계정을
  비활성화하거나 권한을 회수한다. A1의 기존 세션에서 관리자 조회·저장·게시와 미공개 사진 조회를
  확인하고 신규 로그인도 시도한다. 같은 시간에 A2의 정상 관리자 조회를 대조군으로 실행한다.
- **합격 기준과 증거.** 확정된 회수 기한 안에 A1의 관리자 접근이 거부되고 DB·게시본·파일이 변경되지
  않아야 한다. A2의 정상 세션 조회는 계속 성공해야 한다. 회수 실행 시각, 반영 확인 시각, 적용 대상,
  HTTP 결과와 감사 근거를 보존한다. 세션·인증 토큰 원문은 증거에서 제거한다. 요청별 HTTP 코드와 반영
  기한은 [G05](api-operation-test-matrix.md#g05)에서 확정한다. 우선순위 P1.

#### L04 인증 실패 제한·개별 계정

- **근거·연결 항목:** 고시5·6 / S05·Q01

## 4. 기존 테스트와 달라지는 핵심

1. **업무 감사 이력과 개인정보 접속기록을 구분한다.** 기존 PUBLISH/UPDATE_DRAFT 이력만으로 개인정보
   조회 추적·필수 보유·점검을 검증했다고 처리하지 않는다.
2. **계정 비활성화 후 이미 발급된 세션을 시험한다.** 로그인 거부 테스트만으로 권한 회수 완료를
   판단하지 않는다.
3. **삭제 후 백업 복원까지 추적한다.** 감사 보존과 파기 근거를 먼저 정하고, FK 삭제 실패·old
   backup의 개인정보 재등장을 실제 복구 절차에서 확인한다.
4. **법정 기록과 비밀정보 비노출을 동시에 만족시킨다.** S13의 “비밀 토큰 로그 금지”를 “접속자/IP 등
   필요한 모든 기록 금지”로 확대하지 않는다. 접근권한·암호화·보유기간으로 보호한다.
5. **사고를 확정 유출만으로 한정하지 않는다.** 현행 시행령의 유출 가능성 통지 조건을 별도 분기로
   추가한다. 모의훈련은 가짜 사건으로 수행하며 실제 기관 신고·이용자 발송은 하지 않는다.

법정 보유기간은 **3년/1년/2년**을 각각 권한변경 이력/기본 접속기록/조건부 접속기록에 연결한다. 이를
전 데이터의 보유기간으로 확대하지 않는다. 기본 접속기록1년으로 설계했더라도 처리 규모·항목이
바뀌면2년 적용 여부를 재판정한다.

## 5. 적용 확인 후 진행할 순서

1. L01·L11로 실제 데이터 흐름과 운영 주체·처리 근거·수신자·해외 조회를 확정한다. 인물
   사진·IP·localStorage·AI 자료 본문도 포함한다.
2. L03~L08로 기존 계정 회수, 로그인 제한, 접속/권한 기록, 암호화의 구현 공백을 검증한다. 현재 코드는
   충족 미확인 상태다.
3. L02·L09·L10으로 처리방침·권리행사·보유/파기·감사·백업 정책을 맞춘다. 필요한 관리 절차는 API
   추가와 별도로 준비한다.
4. L12~L14를 R15 운영 대응 훈련에 연결한다. 통지·신고의 대상과 시계를 각각 기록하고 접수처/간주
   요건은 실제 사고 대응 시 재확인한다.
5. L15~L17의 조직·규모·위치정보·인증 적용 결과와 근거를 기록한다. 기능이 없어서 비적용인 항목은 기능
   도입 시 재검토 조건을 남긴다.

전체 상태: **L01~L17의 계획 작성·이번 검토에서 미실행**. 암호화·최소 권한 등 기존 기능과 테스트가
일부 존재하므로 전체 기능이 미구현이라는 뜻은 아니다. 법적 의무 중 일부는 내부 관리·계약·교육·권리
대응 같은 운영 증거가 필요하므로 테스트 커버리지 수치로 준수율을 계산하지 않는다.
