## 주니어 개발자 관점에서 평가

공개 API의 입력 검증과 초안 저장은 기존 코드에서 시작할 수 있다. 명세의 케이스 ID를 알아도 어느
테스트에서 어떤 값을 그대로 쓰고 어떤 값을 응답에서 얻어야 하는지는 문서를 오가며 판단해야 했다.
분산 DB·MSA·클라우드 검증은 운영 구성과 기준이 정해진 뒤에야 실행할 수 있는 항목이 많다.

| 범위                 | 명세만 보고 시작할 수 있는 수준                                                                                                      | 첫 작업                                                                                               |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| 공개 API·요청 검증   | 상태 코드·입력값·대조군이 구체적이어서 기존 MVC 테스트를 재사용할 수 있다.                                                           | F09의 국가 코드 정상·거부·빈 결과를 구분한다.                                                         |
| 관리자 쓰기·동시성   | 테스트 계정·세션·편집권·버전 준비가 필요하다. 순서가 틀리면 목표 분기에 도달하기 어렵다.                                             | 기존 PostgreSQL 흐름에서 F12의 오래된 ETag 비교를 실행한다.                                           |
| 오류 로그·감사       | 기존 테스트는 응답이나 DB 결과를 일부 검증한다. 직접 캡처한 로그와 응답의 식별자를 비교하는 절차가 필요하다.                         | LOG01에서 같은 요청의 ERROR 로그를 캡처한다.                                                          |
| MSA·분산 DB·클라우드 | 현 구성에서 연습할 수 있는 검증은 일부다. 내부 계약, 실제 서비스 접속 경로, 운영 임계값이 필요한 항목은 승인된 기준을 먼저 확인한다. | DDB02의 단일 풀 대조를 격리 DB에서 시작한다. 다중 서비스·클라우드 결과는 해당 스테이징에서 기록한다.  |
| 개인정보·권한 기록   | 적용 여부와 기록 항목은 담당자가 확정해야 한다. 가짜 계정으로 실행할 시나리오는 작성할 수 있다.                                      | 예를 들어 L06 적용 범위가 확정되면 승인된 테스트 계정의 조회 한 건을 재현하고 기록이 남는지 확인한다. |

## 테스트를 추가하는 순서

1. API 경로 또는 케이스 ID 하나를 고른다. 입력·응답은 API 정책과 OpenAPI에서 확인하고, 저장 결과는
   실행 상세 명세를 읽는다. 모호하거나 다른 경우 연결표의 G 쟁점을 확인한다.
2. 같은 입력에서 정상 요청부터 실행한다. 실패 케이스는 검사할 값 하나만 바꾼다. 예를 들어 오래된
   ETag를 검증하면서 CSRF도 빼면 요청이 먼저 인증 단계에서 거부될 수 있다.
3. DB나 프록시 없이 규칙을 검증할 수 있으면 서비스 또는 MVC 테스트를 쓴다. SQL 제약·잠금·커밋·감사
   기록에는 PostgreSQL을 사용한다. 앱과 수집기 사이의 연결, 클라우드 권한과 라우팅은 실제 스테이징
   진입점에서 실행한다.
4. 요구사항을 새로 구현하거나 수정할 때는 기대하는 이유로 실패하는 테스트부터 실행한다. 기존 동작을
   보강하는 회귀 테스트는 현재의 정상·실패 대조군을 검증한다. 준비 단계에서 실패한 실행과 제품
   동작의 실패를 구분해 기록한다.
5. HTTP 상태·본문·헤더와 업무 결과를 각각 단언한다. 쓰기 실패의 DB 후조건은 트랜잭션 종료 뒤
   조회한다. ID·토큰·ETag는 응답에서 받은 값을 사용하고, 시각이나 순서를 검증할 때는 테스트
   Clock·장벽·기한 있는 상태 조회를 활용한다.

PostgreSQL 통합 테스트는 기존 클래스와 같이 `@Tag("postgres")`와 테스트 컨테이너 기반을 사용한다.
해당 기반은 테스트 계정과 JP 국가를 준비한다. 업무 데이터는 API로 새 ID를 만들어 다른 테스트
데이터와 분리한다. HTML 결과는 `backend/build/reports/tests/<작업 이름>/index.html`에서 확인한다.
OpenAPI 실제 응답 검사는 필수 응답 조합이 필요하므로 전체 `postgresContainerTest`를 실행한 뒤 저장소
루트의 `pnpm --dir tools/api-contract test:integration`을 사용한다.

## 예제 1 공개 목록의 정상·오류·빈 결과

`GET /api/v1/cities`에서 국가 코드의 **형식 검증**과 **검색 결과가 없는 경우**를 구분한다.
`CityListControllerTest`의 `MockMvc`와 서비스 대역을 재사용한다.

| 준비와 입력                                                                   | HTTP와 본문                                | 추가로 확인할 것                                                                        |
| ----------------------------------------------------------------------------- | ------------------------------------------ | --------------------------------------------------------------------------------------- |
| JP 결과에 PREPARING 도시 1개를 반환하도록 준비하고 `countryCode=JP`를 보낸다. | `200`, `items` 1개, `visibility=PREPARING` | ID를 `"9007199254740993"`으로 준비해 응답에서 숫자가 아닌 문자열로 유지되는지 검사한다. |
| KR 결과를 빈 목록으로 준비하고 `countryCode=KR`를 보낸다.                     | `200`, `{"items":[]}`                      | 형식은 유효하므로 서비스가 KR로 한 번 호출된다.                                         |
| `jp`, `JPN`, 빈 문자열을 독립 요청에 넣는다.                                  | 각각 `400 INVALID_QUERY`                   | 잘못된 요청으로 도시 조회 서비스가 호출되지 않아야 한다.                                |
| 쿼리에서 `countryCode` 자체를 생략한다.                                       | `200`, 준비한 전체 목록                    | 서비스 입력이 `null`인 경로를 확인한다.                                                 |

준비값이 동일한 세 가지 거부 입력은 JUnit의 매개변수 테스트로 묶을 수 있다. 정상·빈 목록·생략은
서비스 호출과 응답의 의미가 다르므로 각각 검증한다.

## 예제 2 초안 저장에서 오래된 버전 거부

이 케이스는 편집권과 인증이 유효하다는 전제에서 이전 버전만 막는지 확인한다.

1. 테스트 관리자 A1의 세션과 CSRF를 준비한다. 새 도시 생성의 `201`과 `city.id`를 사용한다. 그 도시의
   편집권을 획득해 `leaseToken`을 받고, `GET /api/v1/admin/cities/{cityId}/draft`에서 ETag E0을
   얻는다.
2. MIN 본문에서 `tagline`만 `최신 소개`로 바꾼다. `PUT /api/v1/admin/cities/{cityId}/draft`에 같은
   세션·CSRF·편집 토큰과 `If-Match: E0`을 보낸다. `200`과 새 ETag E1을 받는다. 저장된 소개·편집
   버전·감사 상태를 확보한다.
3. 같은 본문의 `tagline`만 `저장되면 안 되는 소개`로 바꾸고 이전 ETag E0을 다시 보낸다. 합격 조건은
   `412 RESOURCE_VERSION_MISMATCH`다. 초안을 다시 읽어 ETag가 E1이며 소개·편집 버전·성공 감사 건수가
   거부 직전과 같은지 확인한다.
4. E1을 사용한 정상 대조 요청을 별도 케이스로 실행하고 `200`과 갱신된 값을 확인한다. 헤더 누락
   `428`과 약한 ETag `400`도 준비 상태를 다시 만들어 독립 실행한다.

E0·E1은 설명에 쓰는 이름으로 실제 문자열을 하드코딩하지 않는다. 헤더 값의 큰따옴표도 그대로
전달한다. 기존 통합 테스트의 인증된 세션 fixture는 초안 검증에 재사용할 수 있으며, 실제 로그인·세션
회수는 해당 인증 케이스에서 검증한다. [F12 If-Match](test-case-execution-draft.md#f12-if-match) ·
[MIN 요청 본문](test-case-execution-draft.md#정상-요청-템플릿)

## 예제 3 로그와 운영 시험을 구현할 때

- **LOG01**은 `CityListControllerTest`에서 재현한다. 정상 요청의 대조군 뒤 서비스 대역으로 예외를
  던지고, 응답에서 얻은 ID로 같은 테스트에서 캡처한 ERROR를 찾는다. 단언은 ERROR 건수·ID 일치·가짜
  예외값 미포함으로 나눈다.
  [로그 캡처 예제](logging-test-spec-draft.md#기존-mvc-테스트에-로그-검사-추가)
- **LOG08·LOG09**는 중앙 저장소가 있는 스테이징에서 한다. 응답 ID를 기준으로 먼저 중앙 조회가 되는지
  확인하고, 서비스 또는 수집기를 다시 띄운 뒤 새 조회 세션에서 같은 ID를 찾는다. 장애를 기록한
  담당자와 조회로 원인을 찾는 역할을 구분한다.
  [이벤트별 기록 예시](logging-test-spec-draft.md#재시작-시험의-기록-예시)
- **DDB02**는 테스트 컨테이너에 연결된 앱의 풀을 작게 만든 뒤 연결을 동시에 빌리고, 제한을 확인한
  다음 모든 연결을 반환한다. 물리 DB가 하나인 시험은 풀 동작의 증거로 기록한다. 독립 DB 격리와
  클라우드 장애 조치는 해당 구성에서 별도 실행한다.
  [풀 고갈 준비와 판정](distributed-db-cloud-test-spec-draft.md#로컬에서-풀-고갈-재현)
- **MSA·클라우드 설정 검증**은 실제 서비스 이름·접속 대상·인스턴스 수·운영 판단 기준을 배포 담당과
  먼저 맞춘다. 연습용 숫자를 바꿔 테스트를 통과시키기 전에, 어떤 값이 운영 합격 기준인지 확인한다.
  [MSA 케이스 작성 예시](msa-test-spec-draft.md#서비스-분리-시나리오의-입력과-기대-결과) ·
  [클라우드 입력과 관측 예시](distributed-db-cloud-test-spec-draft.md#케이스별-입력과-관측-예시)

## 실행 결과를 남기는 예시

| 항목          | F12 테스트 기록에 넣을 값                                                                                                 |
| ------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 케이스와 환경 | F12-STALE-DRAFT, 격리 PostgreSQL, 실제 실행 커밋과 테스트 메서드                                                          |

| 기대와 실제   | `412 RESOURCE_VERSION_MISMATCH`, 재조회 E1·소개·편집 버전·성공 감사 건수. 실제로 확인한 값을 별도 열이나 실행 기록에 기입 |
