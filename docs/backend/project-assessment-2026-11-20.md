# TripeE 프로젝트 평가 보고서

최초 평가 및 재평가: 2026-11-20. 대상은 현재 로컬 작업 트리임. GitHub 원격 CI나 운영 환경은 이번에 확인하지 않았음. 정성 평가는 수치화된 완성률이나 성능 측정치가 아님.

## 종합 평가

핵심 업무 흐름을 검증한 MVP 백엔드임. 이전 평가 후 오류 응답, 게시 Location, 명세 생성 오류가 수정됐고 실제 응답 계약 검증과 초안 처리 분리가 추가됐음. 다만 프론트엔드 실연동, 운영 환경, 부하 성능은 아직 검증되지 않았으므로 배포 준비 완료로 평가하지 않음.

| ------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------- |

JaCoCo 통합 보고서는 **라인 95.55%**, **분기 82.59%**임. 분기 942개 중 164개가 미실행임. 최초 평가의 95.42%·82.55%와는 코드 구조와 분모가 달라 수치만으로 품질 향상을 단정할 수 없음. 커버리지는 요구사항 완성률이 아님. 보고서는 `backend/build/reports/jacoco/combinedContainerCoverageReport/html/index.html`에 있음.

동시 편집 경쟁, 오래된 버전 차단, 롤백, 사진 권한 및 삭제 후 감사 이력을 검증하는 점은 강점임. 계약 검사는 제한된 시나리오와 인증된 MockMvc 세션을 사용하므로 실제 로그인·브라우저·프록시·네트워크를 거친 전체 사용자 흐름의 검증과 구분해야 함. CI 워크플로는 로컬에서 설정을 확인했으며 GitHub에서의 실제 실행은 확인하지 않았음.

## 프로젝트 구조와 리팩토링

- `controller`, `service`, `repository`를 기능별 하위 패키지로 나누고 관리자 도시·국가·태그 모델을 별도로 두었음. 서비스가 컨트롤러 요청 타입을 직접 참조하던 부분과 주요 관리자 서비스의 `ResponseEntity` 반환이 정리됐음.
- `DraftRepository`에서 `DraftContentStore`, `DraftSafetyStore`, `DraftPublicationStore`를 분리했음. 기존 도시 잠금·호출 트랜잭션을 공유하며 PostgreSQL 통합 테스트로 회귀를 확인했음.
- 아직 초안 입력과 DB 응답은 `JsonNode`를 광범위하게 사용하고, 참조 무결성·일부 충돌 판단이 저장소 SQL과 함께 존재함. 공개 도시 목록 저장소는 `service.city`의 조회 모델을 참조하므로 모델 경계도 완전히 일관되지는 않음. 필요한 범위부터 타입 있는 모델과 책임 분리를 고려함.
- 단일 애플리케이션을 유지하며 기능 경계를 다듬는 접근이 현재 팀 규모와 업무 범위에 적절함. MSA 도입 여부는 독립 배포와 운영 요구가 생긴 후 재검토함.

## 기술 선택과 트렌드

Java 21, Spring Boot 4.1.2, Spring Security, Spring Data JPA·Querydsl, PostgreSQL, Testcontainers는 현재 프로젝트의 요구에 맞는 선택임. 동적 조회는 Querydsl, PostgreSQL 전용 JSON 집계·잠금은 JDBC로 유지해 특성을 활용함. 복수 접근 방식의 트랜잭션·영속성 컨텍스트 주의점은 유지해야 함.

Spring Data는 OpenFeign Querydsl 포크를 best-effort로 지원하므로 업그레이드 시 호환성 테스트가 필요함. [Spring Boot 요구사항](https://docs.spring.io/spring-boot/system-requirements.html), [Spring Data Querydsl 지원 안내](https://docs.spring.io/spring-data/jpa/reference/repositories/core-extensions.html).

## 성능 검토

이번 재평가에서 부하 테스트, 응답 시간, 처리량, p95 또는 쿼리 계획은 측정하지 않았음. 아래는 코드 기반 병목 후보임.

| 구간        | 현재 동작                                 | 검토 방향                                    |
| ----------- | ----------------------------------------- | -------------------------------------------- |
| 공개 검색   | 전체 공개 도시 조회 후 Java에서 검색·정렬 | 도시 증가 시 DB 검색·제한 및 실행 계획 측정  |
| 초안 저장   | 태그·사진·출처별 존재 확인과 개별 SQL     | 데이터 증가 시 일괄 조회·배치 저장 검토      |
| 사진 전송   | 전체 파일을 메모리로 읽음                 | 동시 다운로드 증가 시 스트리밍과 메모리 측정 |
| 사진 업로드 | 최대 4천만 픽셀 디코딩·재인코딩           | 동시 업로드 제한과 메모리 측정               |
| 프론트엔드  | 주요 App 청크 약 1.14 MB, gzip 약 313 KB  | 모바일 초기 로딩 실측 후 분할 검토           |

공개 응답의 `no-store`는 승인된 정책이므로 캐시 도입은 비공개 전환·안전정보 갱신 정책과 함께 검토해야 함.

## 명세·실제 연동·운영의 남은 사항

- OpenAPI 26개 경로·39개 작업과 컨트롤러의 메서드·경로가 정적으로 일치함. 이는 각 요청·응답과 업무 동작 전체가 명세에 맞는다는 의미는 아님.
- 공개 화면은 정적 데이터, 관리자 화면은 `createDemoService(localStorage)`를 사용함. 프론트엔드 담당자와 실제 API 연결 및 브라우저 E2E 검증이 필요함.
- AI 제공자는 미정임. 요청·응답 검증 구조는 있지만 실제 후보 생성은 사용할 수 없음.
- 로그인·AI 요청 제한, DB 버전별 마이그레이션, 상태·메트릭 관측, 백업·복구 절차가 필요함. 세션과 사진 저장은 현재 서버 인스턴스에 의존함.
- `docs/project-status.md`에는 서버 구현 전이라는 오래된 상태가 있고, `docs/backend/backend-api-scope.md`에는 이미 구현된 잠금 반납이 예정 작업으로 남아 있음.
- 백엔드와 여러 문서가 로컬에서 아직 추적되지 않은 상태임. 원격 반영이나 PR 상태는 이번에 확인하지 않았음.

## 권장 작업 순서

1. 422 필드별 오류 전달 및 남은 오류 처리 범위의 계약 검증 보강.
2. 프론트엔드 담당자와 API 연결·브라우저 E2E 검증 및 명세 차이 조정.
3. 운영 전 DB 마이그레이션·백업·복구, 인증 요청 제한과 관측성 준비.
4. 실제 예상 데이터와 동시 요청 기준으로 성능·쿼리 계획·사진 메모리 측정 후 개선.
5. 남은 모델 의존성·JsonNode 검증·저장소 업무 규칙을 필요도에 따라 단계적으로 정리하고 오래된 상태 문서를 갱신.
